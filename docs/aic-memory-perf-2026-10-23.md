本文保留节点优化前的失败基线。节点共享原型优化后的用户真机结果已记入[第 1 步记录](aic-node-prototype-step1.md#用户真机结果)：挂载/首帧/120 帧零错误、零分配失败，用户确认画面和触摸下拉正常；不覆盖下文原始结果。

本轮按 `pocket.features.json` 的 `aic-diagnostic` profile 裁剪共享 App。编译通过，**S4 挂载期间底层分配失败，未进入首帧**。本轮没有稳态、FPS、`turn_max` 或业务流量结果，不能判定共享 UI 已通过板端验收。

## 失败证据与解释边界

日志先抛 `TypeError: not a function`（调用链含 `mount`），随后输出 S4 采样、8 条 `heap-fail`、`bundle eval failed`，最终 `run finished with code -1`。8 条请求的 `charged` 依次为 100、100、132、132、78、78、132、132 bytes，均为 align=8、stage=S4-mount。后续 dump 重复同一组记录，不是另外 8 次失败。

底层分配失败已被直接记录；结合失败发生于组件挂载链，可将本次 TypeError 视作 OOM 伴随症状。S3 无分配失败，系统历史峰值从编译后的 4.48 MiB 升至挂载阶段的 6.52 MiB，当前瓶颈已落到挂载阶段。

S4 的 `js malloc_size` 为 2.71 MiB / 5 MiB，未显示配额触顶；`guest_peak` 4.52 MiB 是分配器记账口径，不能直接当成 QuickJS 配额峰值。日志明确证明底层堆失败，提高 JS 配额不会增加系统堆容量。

系统历史峰值占总堆约 93.2%。`总堆 − sys_max = 500,872 bytes` 只是峰值记账差额，不是失败瞬间可成功分配的空间。S4 的空闲总量 1,117,896、最大空闲块 267,064 和 8,994 块碎片均在异常后采到；它们显示堆已明显碎片化，但不能反推失败当刻的块分布，也不能证明只需增加约 0.48 MiB 就能成功挂载。成功挂载的总需求与缺口仍未测得。

## 与历史结果的关系

[2026-10-12 完整 App 诊断](aic-memory-optimization.md#214-完整-ui-断点实测2026-10-12p0)的 S3 `sys_max` 为 5,478,612，本次为 4,693,452，少 785,160 bytes（约 14.3%）；S4 `sys_max` 从 6,876,604 到 6,839,160，仅少 37,444 bytes（约 0.54%），两轮均失败。

这是跨版本、跨功能组合的观测，不是单项 feature 的受控 A/B，不能把差值归因给某个开关。两次 S4 都是失败截断峰值，接近并不代表裁剪无收益；完整需求未被观测到。离板单项实验仍分别见 [terminal](terminal-feature-heap.md)、[MCP](mcp-feature-heap.md)、[transport](transport-feature-heap.md)、[UI](ui-feature-heap.md)，不与板端数字直接相减。

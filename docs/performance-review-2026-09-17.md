# 大数据量卡顿：代码审阅与性能基线

审阅日期：2026-09-17。源码基线：`c3f9caf`；PocketJS 子模块：`2d20ddad228db52fa29ad7d7d06f44e8672164af`。

**首要瓶颈是每次增量接收都重排全部日志历史，其次是隐藏视图持续计算和可见节点整批重建。另有一个确定的刷新缺陷：日志满 500 行后，新内容不再触发版本更新，会表现为接收区停住。**

在本机宿主使用的 QuickJS 库中，500 条 × 256 B 的历史，一次新增帧同步的中位耗时为 **71.830 ms**；500 条 × 4 KiB 的历史，一次重排为 **1116.573 ms**。这些数值只覆盖核心层，不包含 Vue 更新、原生文字布局和绘制，已经超过 [SPEC §5.2](../SPEC.md) 的 JS 每帧 < 4 ms 预算。

本次交付为审阅文档、复测工具和原始结果；没有修改应用行为。未取得用户实际协议、吞吐和显示选项的复现数据，以下对收发与终端两种模式分别判断，不把微基准等同于用户现场帧率。

## 2. 数据路径与卡顿放大机制

```text
串口/网络 worker
  → 无容量上限的事件队列（JSON + Base64）
  → 每 tick 全量 poll / JSON.parse / Base64 解码
  → FrameCoalescer（逐字节 number[] 累积）
  → MessageBus
      ├─ 同步 terminal.feed（收发模式也执行）
      ├─ LogView.sync → 全历史 rebuild（终端模式也执行，除非暂停显示）
      └─ MCP 增量读行格式化（服务运行时）
  → 可见行 .map / Vapor fragment 替换
  → 原生节点结构变化 / Taffy 重建 / 文字布局 / 绘制
```

宿主在 UI 线程依次执行 `guest.frame()`、`surface.tick()`，随后计算绘制哈希（[main.rs](../host/macos/src/main.rs)，L1354、L1359、L1427）。长 JS 工作会推迟后续布局、绘制以及下一 tick 的输入处理。上游 worker 仍可继续生产数据；下一轮 poll 的工作量会增加。这条放大链由代码确认，实际队列增长速率还需要持续流量实测。

已有的窗口化只限制了挂载行数（[transfer.tsx](../app/transfer.tsx)，L327–333），没有限制历史格式化工作量。绘制哈希相同时省掉 paint，也不能省掉此前已完成的 JS 工作。

### F1：满行后的“卡住”包含刷新正确性问题

位置：[core/logview.ts](../core/logview.ts) L143–158；[app/session.ts](../app/session.ts) L839–847；[app/transfer.tsx](../app/transfer.tsx) L278–280、L327–333。

`sync()` 返回的 `added` 是 `重排后的行数 - 重排前的行数`，应用只在 `added > 0` 时递增 `logVersion`。达到 500 行后，每次新消息挤掉旧行，总行数仍是 500，因此 `added=0`，即使内容已经改变也没有通知 UI。

复现：先同步 500 条单行消息，再追加 `LATEST`。两种引擎都得到 `rows=500`、`added=0`、`lost=0`，最后一条 `msgId` 从 500 变为 501，但 `appWouldBumpLogVersion=false`。这是确定的数据更新信号缺陷；源码中日志行依赖该信号，实际画面可能要等滚动、设置变化等其它依赖触发后才追上。此处没有进行像素级复现。

建议：把内容版本或 `changed` 与行数净增量分开；新增、裁剪、内容替换均可使版本变化。保持隐藏 TX 没有可见变化时的合理行为。回归需要覆盖：满行后追加、较长旧帧被短新帧替换导致行数减少、暂停恢复、滚动锁定以及末条数据可见性。修正通知后将暴露更多真实渲染工作，应紧接着处理 F2/F5。

### F2：增量同步中的全历史重排是主要瓶颈

位置：[core/logview.ts](../core/logview.ts) L143–158、L177–250；[core/format.ts](../core/format.ts) 的 `formatLogParts`；[core/ansicolor.ts](../core/ansicolor.ts) 的 `feed`。

每次有新消息，`sync → rebuild` 遍历全部 `entries`：重新解码原始 payload、重放 ANSI 状态、拆硬换行、逐字符折行、分配 `LogRow`。最后才把所有生成行裁到 500。宽度缓存减少了单字符 native measure 调用，无法省掉这些字符遍历。

令保留消息数为 H、平均负载为 B、生成显示行数为 R：一次同步需要处理约 H×B 字节及 R 个临时行；启动积累阶段，逐条同步的总工作随累计历史呈二次增长；满容量后的每个增量仍重处理整段历史。HEX 将文本长度扩为约原始字节数的三倍，进一步增加折行工作。

实测：同样 256 B 帧，20 / 100 / 500 条历史重排的 QuickJS p50 分别是 **3.286 / 14.297 / 72.541 ms**。真实追加 1 帧后 `sync` 为 **71.830 ms**；无新增时的 `sync` 为 **0.013 ms**。这些结果将问题指向重排路径。

建议：追加时只解码/扫描/折行新消息，保留旧行与稳定身份；按行数和字节额度批量裁剪，避免先生成全部历史行再删除。格式、字体或宽度变化才使对应缓存失效。ANSI 跨包尾序列和当前颜色必须持续维护；全量重放时需要保存历史头部解析状态，不能简单从默认颜色重新开始。优化需保护 SPEC 中的跨帧颜色、无损 HEX、暂停/溢出提示语义。

### F3：500 行并不意味着只持有 500 行对应的数据

位置：[core/logview.ts](../core/logview.ts) L90–100、L154–175、L218–220；[core/message.ts](../core/message.ts) 的 `RingBuffer.push`。

总线按 1000 帧 / 256 KiB 裁剪，而 `LogView.entries` 是另一个保留消息引用的数组，仅按 500 **帧**裁剪。总线逐出的旧 payload 因为仍被 `entries` 引用而继续存活；行数限制在重排结束后才执行。隐藏 TX 也会占据 entries。

在默认总线限制下分批同步 500 个不同的 4 KiB payload 后，实测 `entries` 持有 **2,048,000 B（约 1.95 MiB）**，总线仅持有 **262,144 B**，显示行仍为 500。该视图每次重排 p50 **1116.573 ms**。12 个 48 KiB 帧也能保留 589,824 B，重排 p50 **365.065 ms**。

这不是永久无界泄漏：entries 有帧数上限。但它具有独立于总线的保留窗口，不能用总线的 256 KiB 推断应用内存或排版上限。以上只计 payload，未计字符串、颜色数组、终端网格及原生缓存。

建议：为 UI 历史定义明确的字节预算，原始帧与缓存按预算统一回收；明确格式切换还能重放多远。若改变用户可见历史保留语义，先补 SPEC。超长单帧的接收/暂存/显示也要有额度，保证裁剪提示和原始字节语义可解释。

### F4：模式切换没有停止隐藏视图的重计算

位置：[app/session.ts](../app/session.ts) L78–86、L827–847；[app/app.tsx](../app/app.tsx) L244–251；[core/term.ts](../core/term.ts) L343–386。

每个 RX 在总线同步订阅者内执行 `terminal.feed()`，即使当前是收发模式。切到终端后，`pumpSession()` 仍执行 `logView.sync()`，唯一开关是 `rxPaused`。因此收发模式的“暂停”只能停日志同步；终端解析、宿主 drain 和编解码仍执行。

实测 16 KiB ASCII 的 `terminal.feed` p50 **17.028 ms**（80×24，9999 行回滚，测量过程中未填满回滚），已经能占掉一个 60 Hz 帧周期。终端模式叠加 F2 后，隐藏日志也能主导卡顿。

建议：将持续接收/协议状态、历史保留、可见格式化分开。先让不可见的日志推迟排版，同时按既定预算保留数据和消费游标；切回时分批构建视图。终端状态涉及模式切换后屏幕保留和 DSR/DA 应答，直接取消订阅会改变行为。可先优化终端解析及分片调度；若采用延迟重放，需定义有界缓存、追赶和应答时序，再对齐 SPEC。

### F5：窗口化列表仍会整批创建与移除节点

位置：[app/transfer.tsx](../app/transfer.tsx) L327–333、L414 起；[app/terminal.tsx](../app/terminal.tsx) L317–329、L341–346、L433；[core/term.ts](../core/term.ts) L41–46、L386。

本次重新执行 `npm run build` 后，两个列表都编译为 `createNodes(() => visibleRows()/visibleLines().map(...))`。本地 `@vue-jsx-vapor/runtime` 3.2.19 的 `resolveValues` 会停止旧 effect scope 并重新求值；`resolveValue` 对 fragment 执行旧节点移除、新节点插入（`node_modules/@vue-jsx-vapor/runtime/dist/vapor.js` L79–114）。这条代码路径没有按稳定行身份增量复用。

当前 `LogRow.key` 每次重排都重新分配，列表也没有使用该 key。终端只有全局版本，没有每行 dirty/revision：一次 feed 会让可见行全部重新读取并计算 `rowRuns`，游标和选区也处于行构建路径。与 SPEC §5.2 的“只重绘脏行”有明确差距。

原生层的结构变更会置布局 dirty；[PocketJS layout.rs](../vendor/pocketjs/engine/core/src/layout.rs) L341–429 的结构脏路径会清空并重建对应根的 Taffy 树。因此几十个可见行仍可触发大量宿主节点操作与排版。具体耗时占比尚未测量，不能把全部卡顿归因于 GPU 或字体。

建议：采用经过当前 Vapor 适配器验证的稳定列表复用机制或固定可视行槽，按行版本更新文本/颜色；终端维护行 dirty/revision，缓存 run，光标/选区单独更新。只补 `key` 不能自动改变当前 `createNodes/map` 路径，需要检查编译结果和节点创建/释放计数。保留仓库要求的 absolute 布局、Portal、命中底色等约束。

### F6：高吞吐时，队列与单 tick 工作量没有上限

位置：[com_serial.rs](../host/macos/src/com_serial.rs) L174–175、L247–255、L303–337；[com.rs](../host/macos/src/com.rs) L177–193、L303–322；[bridge/com.ts](../bridge/com.ts) L154–166；[core/session.ts](../core/session.ts) 的 `poll/handleEvent`；[core/framing.ts](../core/framing.ts) L68–92；[core/base64.ts](../core/base64.ts) L22–55。

串口/网络事件使用无界 `mpsc::channel`；`poll` 一次 drain 到空并拼接整个字符串。JS 随后一次 split/parse 全部事件并同步处理，没有事件数、字节数或耗时额度。输入事件与 IO drain 共享 UI tick，慢帧后的积压会扩大后续批量。

接收数据在 Rust 中做 Base64/JSON，JS 中再扫描两遍 Base64 并分配 typed array；合流器又逐字节 push 到 `number[]`，最终转回 `Uint8Array`。合流只有静默条件，没有最大帧字节数或最长等待条件。同批事件共用 `nowMs`，一批可聚成大帧；超过总线容量的单帧还可能在终端处理后立即被总线逐出，日志/MCP 只看到溢出结果。

实测把 1 MiB 按 256×4 KiB 处理：**Base64 解码 p50 306.421 ms；合流 p50 111.043 ms**。这两项不含 JSON/Rust 编码/终端/日志，说明高吞吐原始接收本身也需预算；低波特率下它们是否主导延迟仍应按实际字节率测量。

建议：为队列设字节上限，为 tick 设置处理额度并保留 FIFO；控制事件要保证可达，定义 TCP 背压以及串口/UDP 溢出行为和可见计数。合流改为分块缓冲/游标、一次性连续拷贝，并定义最大帧/等待边界；协议语义变化先更新 SPEC。后续可评估桥接二进制批次以减少 Base64/JSON，需同步 bridge 契约、宿主和 sim host，核心层仍保持纯 TS。

### F7：一次显示设置变更造成两到三次重排

位置：[app/session.ts](../app/session.ts) L414–421；[core/logview.ts](../core/logview.ts) L112–135。

`applyLogFormat()` 先 `remeasure()` 重排，再 `setShowTx()`（若值改变则重排），最后 `setFormat()` 再重排。普通调用两次；MCP 运行态变化导致 TX 显隐改变时可达三次。普通颜色/时间戳开关也会清掉字宽缓存。

500×256 B 下，模拟普通调用链的 QuickJS p50 **144.238 ms**，p95 **259.536 ms**。这直接影响 HEX/颜色/字号等切换后的停顿；大历史下会放大。

建议：集中提交格式、显隐、字体和宽度变更，只重排一次；字宽缓存仅在度量语义改变时失效。`setFormat` 对无变化输入可直接返回。

### F8：终端回滚与字符串写入是后续优化点

位置：[core/term.ts](../core/term.ts) L289–294、L343–353、L427–460、L1377–1379。

终端逐字节 `Array.from`，ASCII 解析分支反复创建空数组；每个可打印字符通过 `slice + 字符 + slice` 改写行文本。回滚满后每滚一行 `shift()`；一次缩小回滚上限也循环 `shift()`。

QuickJS 在回滚已满时新增 64 个空行，回滚上限 0 / 9999 / 100000 的 p50 为 **0.246 / 0.456 / 2.031 ms**。该开销随上限增长，但默认配置下这组操作仍低于 F2，故列为 P2。80 列与 240 列的 16 KiB feed 分别约 17.028 / 16.745 ms，本组数据没有证明加宽会显著恶化；逐字符字符串替换的分配占比需要继续剖析。

建议：回滚采用真正的环形索引，批量裁剪；减少逐字节临时对象，在保持宽字符/组合字符/ANSI 行为的前提下评估可变行缓冲。终端缓存应与 F5 的行版本设计一起进行。

| 合流 1 MiB，256 个 4 KiB 块 | 111.043 | 114.189 | 4.481 |
| Base64 解码 1 MiB，256 个 4 KiB 块 | 306.421 | 322.871 | 5.409 |

关闭换行可减少一部分日志 CPU 工作，但长行仍整串交给 `Text`。拖选时 [textsel.ts](../app/textsel.ts) 的 `monoColAt` 还会度量整行及多个前缀，`measureMono` 以完整文本为缓存 key。因此“关闭换行”不应作为超长帧的最终解决方案；原生长行布局/拖选耗时是下一轮测量点。

## 5. 建议实施顺序与验收

1. **先修 F1 的内容更新契约，同时为持续流量补可见性断言。** 验证满 500 行之后连续新消息仍显示，滚动锁定与选区语义正确；单独修通知不等于修性能。
2. **处理 F2/F3/F7：增量排版、历史字节预算、设置原子重排。** 这是已实测收益空间最大的部分。基准应显示追加工作主要随新数据量增长，而非重做全部历史。
3. **处理 F4/F5：隐藏日志延迟排版、可视行复用、终端脏行。** 用宿主节点创建/移除计数确认：更新一行时，其余可见行节点保持；终端单行变化只重新生成相应 run。
4. **处理 F6：接收背压与 tick 额度。** 基于实际速率设计额度，避免简单每帧丢弃超额字节。保持 FIFO、控制事件和溢出可见性。再依据 profile 处理 F8 等次级分配热点。

建议在既有 release 宿主中加阶段计时：Rust `com.poll` 的队列字节数/最老事件等待时长、JS 事件解析/Base64、合流、terminal.feed、log.sync、MCP、Vapor flush、`surface.tick`、绘制；采样输出 p50/p95/p99/max。测输入投递到可见更新的墙钟延迟，关联 RSS、JS heap/GC、行对象/原生节点创建量。避免逐字节日志干扰测量。

验收矩阵：

| 维度 | 场景与断言 |
|---|---|
| 规格基线 | 真串口 115200 满速持续接收，至少 60 s；无接收丢帧，JS 帧耗时按 SPEC < 4 ms 目标统计 |
| 高频小包 | 64/256 B 帧，历史跨过 500 行和 1000 帧边界；最新序号持续可见 |
| 大包/洪峰 | 4 KiB 持续流、48 KiB 突发、>256 KiB 瞬时批量；内存稳定在明确额度，丢弃计数准确，UI 可响应 |
| 显示选项 | ASCII/HEX、ANSI、时间戳、换行开关；关闭换行时包含长行拖选 |
| 模式 | 收发/终端切换，暂停恢复；终端历史和查询应答保持正确，MCP 门控不变 |
| 用户操作 | 贴底/上翻锁定、选区/复制、HEX 切换、设置应用、窗口 resize；统计输入延迟，建议 p95 < 50 ms，作为新增验收目标先记录到 SPEC |
| 长时运行 | 默认 9999 与最大 100000 回滚；稳定吞吐下队列/RSS 达到平台期，不随运行时长持续增长 |

现有 [flood.test.ts](../host/macos/mcp/flood.test.ts) 主要检查计数对称、连接存活、`frames rendered > 0` 和 PNG 文件头。400 次 send 逐条等待 RPC，生产速率受应用处理速率限制；`>0` 可能仅由启动时绘制满足，无法证明洪峰期间持续刷新，也没有可见末条序号/帧预算/输入延迟断言。其 loopback 路径不经过真实 IO worker 与 Base64 事件桥。应保留功能测试，另加独立生产者的持续流量和上述性能断言。

在修复前，暂停日志显示、清屏、关闭非必需的 HEX/颜色解析可以缓解部分场景；暂停不停止终端解析，清屏也不清终端回滚。这些操作不能解决满行刷新缺陷、隐藏日志和宿主积压。

## 6. 复测命令

在仓库根执行，产物写入临时目录，不读取或覆盖个人配置。QuickJS 路径需要已有 release 宿主构建产物与 macOS C 编译器。若存在多套 `rquickjs-sys` 产物，应选择与当前宿主匹配的目录；本次使用 `rquickjs-sys-09a6920a2c07daf9/out`。

```sh
export PATH="$HOME/.bun/bin:$PATH"
PERF_TMP=$(mktemp -d /private/tmp/pocketcom-perf.XXXXXX)
bun tools/perf-audit.ts > "$PERF_TMP/bun.jsonl"
bun build tools/perf-audit.ts --target browser --format iife --outfile "$PERF_TMP/audit.js"

PERF_QJS_ARCHIVE=$(rg --files -uu host/macos/target/release/build -g libquickjs.a | head -n 1)
PERF_QJS_DIR=${PERF_QJS_ARCHIVE%/*}
cc -O2 -Wall -Wextra -I"$PERF_QJS_DIR" tools/perf-quickjs.c "$PERF_QJS_ARCHIVE" -o "$PERF_TMP/quickjs"
"$PERF_TMP/quickjs" "$PERF_TMP/audit.js" > "$PERF_TMP/quickjs.jsonl"
```

QuickJS 的大历史用例本身包含秒级操作，完整运行需要一段时间；这是被测问题的一部分。输出最后应有 `type: complete`，不要把尚未结束的 JSONL 当完整结果。性能工具用于前后对比，不以本次耗时常量作为 CI 硬门槛。

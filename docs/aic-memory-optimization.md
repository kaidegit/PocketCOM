# D12x 8 MiB PSRAM：PocketCOM 内存优化方案

日期：2026-10-10。范围：当前 AIC / RT-Thread / Vue Vapor / QuickJS-NG 方案。

**2026-10-10 更新：平台层改造已实施**——固件改为 SPI NOR XIP（`.text/.rodata` 原地执行）、删除 data 分区、PSRAM 统一为 RT-Thread TLSF 系统堆（无 PocketJS 私有池），guest 配额 4→5 MiB。本文第 1 节排序与第 2 节内存账描述的是改造前的布局，历史数据保留作对照；新布局与预算语义见 [host/rtthread/README.md](../host/rtthread/README.md) 的"产物与内存"，方案 A（装配/紧凑 UI）、B（字节码）、C（realloc）、D（容量限额）仍是后续工作。

本文是方案评估，尚未实施下列优化。真机数据引用 [AIC 接入记录](../host/rtthread/README.md)，本次核对了源码与本地构建报告，没有重新烧录或进行硬件测试。功能、平台差异和配置上限的正式定义仍以 [SPEC.md](../SPEC.md) 为准；涉及行为变化的方案应先补 SPEC，再实现。

## 1. 建议先走哪条路线

**保留 PocketJS 和 Vue Vapor，以已跑通的精简入口为基线，先定位启动峰值，再恢复有明确内存上限的板端收发功能。** 精简版能启动、出帧、响应触摸，说明这条技术路线在当前硬件上可行；完整应用的启动图和长期数据容量仍需要适配，不能由此推断所有框架路径均无内存问题。

建议按下面顺序推进：

1. **先补阶段测量。** 把 `bundle eval failed` 拆成编译、执行/组件挂载、首帧三个阶段，记录分配失败来自哪里。
2. **优先做 AIC 专用装配与紧凑 UI。** 共用纯 TS 核心，避免导入桌面 `app/session.ts` 时顺带创建所有状态和模型；同时为日志、回滚、输入与 IO 队列设板端上限。
3. **若主要卡在编译，优先验证离线 QuickJS 字节码。** 这是保留较多功能时最值得验证的路线，但当前包加载链尚未支持，不能只换一个打包参数。
4. **同步评估 realloc 瞬时双份分配。** 这是宿主适配层的具体优化点，无需更换框架；收益须用相同应用的前后峰值证明。
5. **最后才调 PSRAM 分区、TLSF 和栈。** 先确定 CMA、SW、最大空闲块与栈高水位，再做受控调整。资源 XIP / 缓存和更大内存硬件是后续选项。

| 方案 | 主要缓解什么 | 预期收益依据 | 成本 / 风险 | 建议 |
|---|---|---|---|---|
| A. AIC 专用入口、装配、紧凑 UI | 编译峰值、初始化与常驻对象 | 精简版已有真机成功基线 | 中；需要定义板端功能边界 | 首选 |
| B. 离线字节码，必要时真正分段加载 | 源码编译峰值 | 跳过板上源码编译；实际峰值待测 | 中高；包契约、加载器、版本兼容 | 保留完整功能时重点验证 |
| C. 改善 realloc 和分配统计 | 瞬时新旧块共存、分配开销 | 当前存在明确的 allocate-copy-free 路径 | 中；涉及对齐、分配头和失败语义 | 测量后优先实验 |
| D. 日志、终端、IO 全链路限额 | 稳态和长时间运行 OOM | 当前桌面容量可超过整板预算 | 中；需要确定截断、背压语义 | 接入收发前必做 |
| E. 字体资源裁剪 / flash 映射或缓存 | CMA 常驻、部分资源运行占用 | 当前包和 `.text` 均占 PSRAM | 裁剪较低；映射/缓存较高 | 作为第二阶段。**其中代码/rodata XIP 已于 2026-10-10 实施** |
| F. CMA / SW / TLSF / 栈重配 | 空间放错区域、池外紧张 | 两区空闲不能自动互用 | 中高；可能挤压显示与系统任务 | 有数据后小步调整。**统一 TLSF 堆 + SW 7 MiB 已于 2026-10-10 实施** |
| G. 更大内存硬件 / 部分原生化 | 完整产品工作集超过 8 MiB | 改变硬上限或对象表示 | 高；硬件/BSP 或维护成本 | 明确止损条件后考虑 |

不能把各方案收益直接相加：裁剪、字节码和 realloc 可能降低同一段峰值；字体裁剪首先释放 CMA，未必增加 TLSF 可用空间。

## 2. 已知基线与真正的内存账

### 2.1 已有三组结果

| 项目 | 完整 UI 原始包 | 完整 UI 压缩包 | 当前精简页 |
|---|---:|---:|---:|
| JS 源码 bytes | 607,688 | 327,877 | 196,719 |
| `.pocket` bytes | 1,153,064 | 873,256 | 526,568 |
| ITB bytes | 2,711,552 | 2,430,976 | 2,084,864 |
| CMA 扣静态区、双 framebuffer 后理论余额 bytes | 408,656 | 688,432 | 1,035,120 |
| SW 扣 TLSF 后理论余额 bytes | 468,992 | 468,992 | 468,992 |
| 真机结果 | bundle eval OOM | 仍 bundle eval OOM | 启动、持续出帧、触摸通过 |

前两列及真机结果来自 2026-10-09 接入记录；精简页大小同时与本地 `dist/aic/memory-report.json`、JS/PAK 文件核对。精简页 PAK 为 **328,064 bytes**。包体积减少证明构建裁剪有效，但不能单独证明编译或运行工作集足够小。

精简页真机记录：

- JS heap 启动采样 **1,163,037 bytes**，随后 **996,688–1,007,882 bytes**。
- TLSF 分配记账启动采样 **2,284,370 bytes**，随后 **2,034,199–2,057,791 bytes**。
- TLSF 分配记账历史峰值 **2,930,837 bytes，约 2.79 MiB**。
- 池容量 **4,249,600 bytes，约 4.05 MiB**；容量减历史峰值为 **1,318,763 bytes，约 1.26 MiB**。

这里的“池用量”是 `pocketjs_heap.c` 累计的申请大小、对齐预留和包装头，**不是 TLSF 实际占用块的完整统计**，还未覆盖 TLSF 元数据、块取整及外部碎片。上述 1.26 MiB 也不是最大连续空闲块，不能全部分配给新功能。

历史 64 位本机编译诊断中，完整 JS 压缩前后请求字节峰值约 **4,935,145 → 3,984,867 bytes**；压缩版在该诊断的 4 MiB 限制下通过编译，却仍在板上 OOM。这组数据只用于判断优化方向：32/64 位对象布局、分配器、原生 UI 与硬件开销不同，不能将本机结果当作板端验收。

### 2.1.1 XIP + 统一堆后的决定性实测（2026-10-10）

XIP/统一 TLSF 堆改造后，完整压缩 UI（JS 328,241 / `.pocket` 897,128）**通过了编译阶段**
（板上不再出现 `InternalError: out of memory`），但 mount 阶段抛 `TypeError: not a function`
后退出。本机同版本 QuickJS probe（`runtime16`，16 MiB 上限、480×272、无 com/svc）给出裁决：

- **完整 UI 本身没有 bug**：16 MiB 上限下 mount 成功、120 帧跑通（`frames=120`，frame_errors=0）。
- **板上 TypeError 是 OOM 的伪装**：分配失败发生在组件树构建中途，取到 undefined 方法并以
  TypeError 形态抛出；不能按字面当运行时缺陷追。
- 真实需求（heap_caps 记账，含 JS + Rust UI + 包装头）：
  **峰值 8,904,442 bytes（≈8.5 MiB）**、eval 后常驻 **7,951,217 bytes**、
  稳态 live ≈8.1 MiB，其中 QuickJS `js_heap` 4,410,058 bytes。
- 板上统一堆 7,340,032 bytes，扣除任务栈/内核/驱动后 guest+Rust 可用约 **6.0–6.4 MiB**
  → **缺口约 2.5 MiB（峰值口径）**，常驻口径也超约 1.6 MiB。

结论：完整桌面 UI 的常驻工作集**超出本板 PSRAM**，符合第 1 节对方案 G 前提的预判；
恢复完整功能只能走 **方案 A（板端专用装配 + 紧凑 UI + 容量限额）**（必要），
字节码（方案 B，约省 0.9 MiB 峰值、编译期工作集）与 realloc 优化（方案 C）作为配套，
或等待更大内存硬件（方案 G）。仅靠平台层调整已无空间——XIP 后 PSRAM 预算与包体积
彻底解耦，静态段只剩 41 KiB。

### 2.2 8 MiB 并不是一个可任意分配的 JS 堆

按当前精简固件报告展开如下。缩进项属于上层区域，不能重复相加。

| 区域 / 项目 | 大小 bytes | 说明 |
|---|---:|---|
| PSRAM 总量 | 8,388,608 | 8 MiB |
| PSRAM_CMA | 3,670,016 | 3.5 MiB；静态代码/数据、内联包、显示等 |
| ↳ 静态区域 | 2,112,656 | 包含 `.text`、`.rodata`、`.data`、`.bss` 与布局占用 |
| ↳ 内联 `.pocket` | 526,568 | **已包含在静态区域内**，不是另一笔占用 |
| ↳ 双 RGB565 framebuffer | 522,240 | `480 × 272 × 2 bytes × 2`，即 510 KiB |
| ↳ 理论剩余 | 1,035,120 | 尚未扣其他驱动分配、对齐、碎片 |
| PSRAM_SW | 4,718,592 | 4.5 MiB；系统动态堆 |
| ↳ 私有 TLSF 池 | 4,249,600 | 4,150 KiB；JS 和原生 UI 等共用 |
| ↳ PocketJS 任务栈 | 393,216 | 384 KiB；`rt_thread_create` 从系统堆申请，在池外 |
| ↳ 再扣上述任务栈后的理论剩余 | 75,776 | 74 KiB；尚未扣其他任务、设备和内核开销 |

另有 JS runtime 的 **4,194,304 bytes / 4 MiB 配额**。它是 TLSF 内部 JS 分配的限制，不是额外分配的 4 MiB，也不是启动时预留的一整块内存。原生 Rust UI 的分配经 `pocketjs_idf_rust_alloc → heap_caps_aligned_alloc` 进入同一个 TLSF 池。

这有三个直接影响：

1. **`js_heap` 未到 4 MiB，TLSF 仍可能先失败。** 池容量只比 JS 上限大 54 KiB，而实际还要容纳原生对象、包装头与碎片；配置本身不能保证“JS 配额一定先触发”。
2. **SW 的 458 KiB 理论余额不是可自由扩池的额度。** 当前宿主任务栈已需要其中 384 KiB。扩大 TLSF 可能让任务创建或未来 IO 先失败。
3. **精简包释放的是 CMA，TLSF 位于 SW，容量没有随之扩大。** 当前还关闭了 memheap 自动绑定，不能假设分配失败会自动借用 CMA；AIC 的 `heap_caps_*` 也忽略 capability 参数，切换 `SPIRAM/INTERNAL` 不会自动获得第二块内存。

### 2.3 当前错误还缺什么证据

`pocketjs_guest_eval()` 调用的是 `JS_Eval(..., JS_EVAL_TYPE_GLOBAL)`，覆盖源码编译和脚本执行。脚本执行又包含模块顶层初始化与 `mount(AicApp)`。因此 **`bundle eval failed` 不能精确区分编译 OOM 和挂载 OOM**。

目前可以确认失败发生在正常帧循环前；不能直接归因于日志填满、终端回滚填满或 framebuffer 翻转，也不能仅凭这一行日志判断是否内存泄漏。

## 3. 先补一次能指导取舍的测量

这是所有方案的共同前置，建议先在 PocketJS fork 增加可关闭的诊断，再用于 PocketCOM。此处描述的是待实现的测量，不是现有 CLI 功能。

### 3.1 分阶段采样

| 阶段 | 边界 | 用来判断什么 |
|---|---|---|
| S0 | 系统启动、申请 TLSF 前后、创建宿主任务后 | 系统 SW 基线和栈成本 |
| S1 | 显示/触摸打开后 | CMA 动态开销与 framebuffer 之外的分配 |
| S2 | 包解析、guest 创建、UI binding / PAK 挂载后 | JS 基础环境、资源与原生 UI 基线 |
| S3 | `JS_EVAL_FLAG_COMPILE_ONLY` 返回后 | 源码编译能否独立完成 |
| S4 | 对 S3 的结果调用 `JS_EvalFunction` 后 | 顶层初始化、组件挂载峰值 |
| S5 | renderer 创建、首帧、120 tick 后 | 首帧与渲染缓存增量 |
| S6 | 各功能开启、持续流量、页面切换、清屏后 | 常驻容量、重复创建、引用未释放 |

S3/S4 的诊断应编译同一份脚本、执行一次，处理返回值所有权并恢复原 guest 的 `frame` 获取和 jobs drain；不要又调用一次完整 `JS_Eval`。分段诊断本身可能改变对象存活时间，最终仍需用生产加载路径复验。

每阶段至少记录：

- 固件与包 hash、入口/功能组合、JS/PAK 大小、区域/池/栈配置。
- QuickJS 的 `malloc_size`、字节码/字符串/atom/对象统计；用 allocator 计数记录瞬时峰值，不能只依赖每秒采样。
- TLSF 记账 current/peak、实际空闲总量、最大空闲块、失败请求大小/对齐、发生阶段和分配来源。
- 系统 SW 与 CMA 的实际余额、任务栈高水位、native UI 节点/资源数、帧错误和 `turn_max`。

最大空闲块可在安全采样点通过 SDK TLSF 的 `tlsf_walk_pool` 汇总；它需要遍历块，不应在每次分配或每帧调用。分配失败路径用预留计数器或固定缓冲，避免诊断自身再次申请堆。OOM 时同时区分 QuickJS 配额拒绝和底层 allocator 返回 NULL；池外的系统分配失败也单独记录。

### 3.2 最小增量实验

以当前精简入口为对照，每个实验单独构建、冷启动：

| 实验 | 新增内容 | 目的 |
|---|---|---|
| E0 | 当前精简页 | 确认基线可重复 |
| E1 | 小容量消息总线 + 纯会话装配，无完整 UI | 分离业务模型初始化成本 |
| E2 | 紧凑接收/发送 UI，固定少量测试数据 | 分离控件树与布局成本 |
| E3 | 有界持续测试流，日志格式切换 | 验证历史、字符串和排版峰值 |
| E4 | 低回滚终端模型，再加终端 UI | 分离终端数据和视图成本 |
| E5 | 设置、软键盘、设备桥等逐项加入 | 找出后续增量成本 |

“只隐藏面板”的实验不能代表删掉模块后的编译成本；“只 import 不创建”仍有该模块的代码成本。每次保存功能组合和启动依赖图，避免实验间同时改 heap、字体和功能导致无法归因。

## 4. 方案 A：AIC 专用装配与紧凑 UI

**目标：复用 PocketCOM 的核心逻辑，让板端只承担实际开放的功能和界面。**

当前完整 `app/app.tsx` 会导入连接面板、收发区、终端、设置弹窗和 `app/session.ts`。后者又在模块顶层创建 `MessageBus`、`Terminal`、日志视图、响应式状态和订阅；即便宿主没有 `com.*`，这些导入与部分初始化成本仍然存在。`app/locale.ts` 也会间接拉入 session，因此连共享工具的依赖边界也要检查。

建议：

1. 保留 `app/main.aic.tsx → app/aic.tsx` 的独立入口。逐步将验证页替换为 480×272 紧凑产品页，不直接挂回桌面 `App`。
2. 将会话装配改为显式工厂或新增板端装配模块：传入内存 profile、可用桥和启用的模型。共用 `core/`，避免复制连接/编码/终端协议实现。
3. 首个产品验证目标只加入串口/回环收发、HEX/文本、清屏和必要参数；网络、终端、MCP、完整设置与软键盘按测量逐项加入。这是建议的 AIC 范围，需先写入 SPEC；当前板端还没有设备 IO 桥。
4. 从构建依赖中移除未启用功能。仅隐藏控件、把创建动作放进按钮回调，只能改变部分执行或节点占用，**无法让已打入同一 IIFE 的代码免于启动编译**。
5. 界面按“连接参数页 / 收发页 / 设置页”分开挂载可见节点；卸载时释放 watchers、onFrame 注册和回调引用，避免关闭页面后对象继续存活。面板沿用 absolute 布局和 Portal 约定。

接收区 `visibleRows()` 与终端 `visibleLines()` **已经做了可见范围渲染**。后续重点是验证节点是否复用、旧 effect 是否释放，以及限制模型历史，不能把“加虚拟列表”当作尚未实现的大收益。

**限制：**惰性创建终端可能改变“收发模式也持续解析 RX、切换后保留终端屏幕”的现有语义。若板端要求保持该行为，应继续维护一个小容量终端模型，延迟的只是视图；如果要完全停用后台终端，必须明确 AIC 的行为差异。

**验收：**不启用的模块从产物依赖中消失；每项功能都有 S3/S4/S5 增量数据；循环开关页面后模型、节点与分配用量进入稳定平台。收益以板端峰值计算，不按源码删除行数估算。

## 5. 方案 B：离线 QuickJS 字节码，必要时分段加载

### 5.1 先验证字节码能否消掉主要启动峰值

在构建机用与固件匹配的 QuickJS-NG 编译应用，板端反序列化字节码并执行，避免启动时再次解析源码、建立编译期状态和执行字节码生成/修正。这与换框架无关，也不等于把 TS 编译为原生机器码。

[QuickJS-NG 官方 C API 文档](https://quickjs-ng.github.io/quickjs/developer-guide/intro/)说明了预编译执行路径及其版本绑定。当前本地 `prepare_quickjs.py` 钉住的是 **QuickJS-NG 0.14.0 对应源码及补丁**，应以这个实际实现为准，不使用系统安装的任意 `qjsc`。

需要打通的工作：

- 构建链产出匹配的 bytecode，并记录引擎源码/补丁、构建选项和兼容标识。32 位板端与构建机之间的兼容性通过加载测试验证，不能根据源码相同直接保证。
- `.pocket` 契约中 section 6 仅是预留字节码类型；当前实际读包逻辑强制寻找 NUL 结尾的 JS section。需要更新包生产、验证、C 读取、guest 加载和版本准入，保留桌面原路径。
- guest 路径使用 `JS_ReadObject(..., JS_READ_OBJ_BYTECODE)` / `JS_EvalFunction`，保持错误处理、`frame` 注册与 jobs drain 行为。
- 只使用受控构建产物，执行前核对兼容性和包完整性。字节码本身不是可不加校验执行的通用交换格式。
- A/B 固件分别携带源码或字节码，不长期同时内联两份；否则 CMA 节省会被抵消。源码路径可保留为独立诊断变体。

**能省：**板上源码编译的临时工作集与启动时间。**仍然要付：**反序列化、atom/常量、函数/闭包、Vue 响应式对象、UI 树、日志与原生缓存。字节码文件也未必小于压缩 JS，因此同时检查 CMA 与 flash 预算。若 S4 挂载才是主因，字节码不能单独解决。

只有不再依赖动态源码求值、相关测试通过后，才评估裁掉编译器代码；不能预先把它算作已获得的 RAM 收益。

### 5.2 分段加载是另一项宿主能力

若单包仍过大，可把基础框架、收发、终端等拆成真正独立加载的单元，按阶段编译/加载，并在阶段间回收临时对象。当前 AIC 产物是单一自包含 IIFE，**没有已经可用的按需模块加载方案**。

仅改成函数封装、静态 import 后延迟调用，仍会在首次 eval 编译函数体。真正分段需要构建器与宿主加载协议配合、共享一份框架运行时、避免每段重复打入 Vue，并界定卸载后的引用与订阅释放。分段只能削峰；如果各段对象最终全部常驻，总工作集仍会回到原来的量级。

**选择条件：**S3 明显高于 S4/S5 常驻值时，先做字节码原型；字节码收益不足，再评估分段。若全功能常驻本身超预算，转向 A/D 或 G。

## 6. 方案 C：降低 realloc 的瞬时双份分配

当前共享 guest 的 `guest_realloc()` 总是：

```text
保留旧块 A → 分配新块 B → memcpy → 释放 A
```

即使新块尺寸更小，也会先申请另一个块。临时需要的内存不只是 `B - A`，而可能是完整的 B 加包装和对齐开销。编译期数组/表扩缩容时，这会放大峰值，并要求存在足够大的连续空闲块。

AIC 还存在同类 `heap_caps_realloc()` 实现，但 **`guest_realloc()` 直接调用 `guest_malloc()`，并未走该函数**。只改下层 `heap_caps_realloc` 不会自动改善 QuickJS 的主要 realloc 路径。

可分两步评估：

1. 先统计 realloc 次数、旧/新大小分布、最大单次请求与峰值时刻。确认它确实主导 OOM。
2. 为 AIC 增加保持对齐和分配头契约的 resize 路径，让 guest 使用它；优先处理可原位缩小、可合并相邻空闲块的增长，失败后保留原块。SDK TLSF 提供 `tlsf_realloc`，但不能把对齐后的用户指针直接传进去：需正确处理 raw 指针、偏移、guest 头、数据移动和记账。

不能只把“缩小时返回原指针”视为完整优化：它可降低本次瞬时峰值，却可能保留大块容量，长期反而占更多内存；如采用此策略，应同时统计实际保留容量。也不能先 free 再 malloc，否则失败时会丢失原数据。

这属于 PocketJS 通用 guest / AIC port 的改进，应在对应 fork 维护，避免产品侧复制运行时。需要覆盖 grow/shrink、零长度、失败后旧数据保留、不同对齐、数据内容与统计一致性，并回归共用 guest 的宿主。

**验收：**同一完整包、相同 heap/栈/GC 配置下，S3/S4 的失败请求减少、池真实峰值下降、最大块足够；不能只看 JS 自报 heap。事前不承诺节省固定百分比。

## 7. 方案 D：为数据和 UI 设置板端容量

这是启动成功后的必要工作。以下风险在当前精简页上尚未发生，也不应被当作本次启动 OOM 的已确认原因。

### 7.1 桌面默认值不适合直接搬到 8 MiB

- `core/config.ts` 默认接收历史和终端回滚均为 **10,000 行**，可配置到 100,000 行。`app/session.ts` 的日志原始字节预算为 `max(256 KiB, historyLines × 256)`，默认即 **2,560,000 bytes，约 2.44 MiB**，还未计格式化字符串和颜色数据。
- `core/logview.ts` 自身构造默认是 500 行 / 256 KiB，但完整应用显式传入配置值；不能只读核心默认值判断实际产品预算。
- `Terminal` 每行有字符串、`fg: Uint32Array`、`bg: Uint32Array`、`flags: Uint8Array`。按默认 80 列，仅属性数组就需 `80 × 9 = 720 bytes/行`；10,000 行属性约 **6.87 MiB**，未计字符、对象和数组头。回滚是逐步增长，并不是构造时预分配 10,000 行，因此主要威胁持续运行。
- 总线与日志历史保存相同 `Message` 的引用，并非必然复制两份 payload；但保留窗口不同，任一窗口仍引用的数据都不能释放。总线的 256 KiB 上限不能代表整个应用占用。

### 7.2 建议的首轮 AIC profile

这些是实验起点，**不是现有默认值或已经验证的承诺**。放在产品装配层显式注入，桌面配置不变；如果开放配置导入，入口处也要应用同样的板端限制。

| 对象 | 首轮建议 | 仍需计入的开销 / 行为 |
|---|---|---|
| MessageBus | 256 帧 / 64 KiB payload 双限制 | 对象头、订阅和临时 drain 数组；正常历史逐出与真实丢包区分 |
| LogView | 200 显示行、原始历史 64 KiB | 字符串、颜色、wrap 临时数据另算；不能沿用 256 KiB 下限公式 |
| Terminal | 启用时先 0–128 行回滚，列/行按实际视口 | 128×80 的属性约 90 KiB；另计当前屏、alt 屏及字符 |
| 发送编辑框 / 单次粘贴 | 4 KiB UTF-8 字节上限起步 | 拒绝或明确分块；不得默默截断要发送的数据 |
| 发送历史 | 10 条且总计不超过 8 KiB | 条数与字节数同时限制 |
| 单次 IO 事件 / 合流积累 | 1–4 KiB 事件，8–16 KiB 合流上限起步 | 达限提前产出；字节顺序不变，展示帧边界变化先补 SPEC |
| 宿主待处理队列 | 32–64 KiB 总字节上限起步，另限事件数 | 每 tick 限字节/事件数；处理速率、背压、溢出计数一起定义 |

以上不能机械相加作为总内存：payload 可能共享，也可能被编解码和格式化放大。应记录所有存活对象和临时副本后的实际峰值。核心已有 `MessageBus`、`LogView`、`Terminal` 容量参数可复用；合流最大字节数等目前尚需新增。

### 7.3 还要堵住限制之前的峰值

`FrameCoalescer` 目前等待静默间隔，不设积累字节上限。连续输入可积累多个拷贝，emit 时再创建连续 `Uint8Array`，短时间存在分块和合并结果两份。后端总线有界也无法阻止这一步先 OOM。需要同时约束事件队列、合流器、单次 flush 和每 tick 工作量。

若延用 Base64/JSON 桥，一个 N 字节事件会产生约 `4 × ceil(N / 3)` 个 Base64 字符，并与 JSON 字符串、解码字节、合流副本短暂共存。不能只按 payload 预算。先缩小单批并及时释放；确有测量收益再讨论二进制桥，改桥契约时同步 sim host 与测试。

显示侧需专项检查：

- HEX 文本通常扩为每字节约 3 个字符；ANSI 逐字符颜色数组会追加占用。格式切换的全历史重建必须受总字节、最大单帧和单行长度控制。
- `LogRow.fg` 的 `subarray` 会保留原 ArrayBuffer；留下很短的一行也可能保活整帧颜色数组。大帧场景要测“保留字节”，不能只数可见行。
- 字符宽度缓存对不断变化的 Unicode 输入会增长；嵌入式可按烘焙字符/替换符限制缓存，或设容量上限。未知字符显示替换符，原始字节仍可通过 HEX 无损查看。
- 持续日志可按测量合并 UI 更新，避免每个小包触发整批节点重建；宿主 60Hz tick 与设备事件 FIFO 语义保留。单纯降低刷新率不会减少历史数据的存活量。

暂停显示时也必须有界。TCP 可用背压；UART 没有流控、UDP 无法让发送方停下时，要明确溢出策略并通过带 `source` 的系统消息/计数告知。不要把输入丢失伪装成正常历史逐出，也不要在过载时每丢一包再生成一个新消息放大队列。

**验收：**连续无换行流、大量小帧、大包、HEX/ANSI、暂停恢复、终端主/alt 屏和格式切换均有上限；清屏/断开后存活容量回落；新限制与分帧语义有核心单测。

## 8. 方案 E：资源裁剪与真正的 flash 资源路径

### 8.1 先做低风险裁剪

精简页仍共用两份完整 i18n JSON；构建脚本从两份语言包所有文案提取字形。可为 AIC 已启用功能生成 zh-CN/en 的 key 子集，JS 文案与烘焙字形使用同一清单；动态拼接 key 和英文回退也要覆盖。减少未使用字号/字重的 atlas，维持 MiSans UI 与 JetBrains Mono 网格约定。

当前 PAK **约 320 KiB**，这是其全部磁盘内容规模；不能凭字体源 TTF 很大就宣称能节省几 MiB。先拆分 PAK 中各 atlas 和元数据，并测实际加载开销，再评估收益。裁剪不能删掉 SPEC 要求的 ASCII、已支持界面文案和替换符；如只保留一种语言或字号，要先定义 AIC 产品差异。

### 8.2 内联、文件加载和 XIP 的区别

**（本节描述的 PSRAM 布局已被 2026-10-10 的 XIP 改造取代，保留作历史依据；现状见 README"产物与内存"。）**

目前 `.rodata` 实际位于 PSRAM_CMA。宿主直接借用内联包，已经没有额外整包加载副本；不能再把“去掉这份副本”当作现成收益。

恢复 `/rodata` 文件系统后用现有 `pocketjs_aic_run(path)` 加载，会从系统堆读取整个包，并因 PAK 借用而长期保留。它可能把压力从 CMA 转到 SW，**不会自动减少总 RAM**。

若要真正节省，需要以下一种新路径：

- **flash 映射只读包/资源：**确保 CPU 可直接寻址、地址生命周期满足 PAK 借用，调整 section、链接和加载流程。确认缓存/访问延迟、对齐及任何 DMA 访问要求；依据 ELF VMA 和真实内存采样验收。
- **分离 JS 与资源生命周期，资源按需读取：**源码在编译执行后释放其独立加载缓冲，PAK 使用有界资源缓存。当前单块内联数组无法释放其中 JS 部分；整体解压进 RAM 也不是按需加载。
- **代码 XIP：**当前精简固件 `.text` 为 1,298,032 bytes，提示存在可评估的代码常驻成本。实际可迁移量需扣必须驻 RAM 的路径。SDK 链接脚本的 `AIC_XIP` 会改变 `.text` 区域，但 `.rodata` 仍指向 PSRAM，不能把开一个 XIP 配置等同于把整个包搬走。

**选择条件：**CMA 成为主要限制，或裁剪/字节码后还需给 SW 腾出空间时再做。资源访问的平均占用下降不能抵消缓存 miss 的临时峰值，必须同时验证启动和实际页面切换。

## 9. 方案 F：受控重配 CMA / SW / TLSF / 栈

**（SW 4.5 MiB + 私有 TLSF 池的布局已被 2026-10-10 改造取代：SW 扩为 7 MiB 统一 TLSF 系统堆、私有池删除、CMA 缩为 1 MiB。本节公式仍适用于后续微调。）**

调整原则是先计算每个区域的峰值需求，再改地址边界。任何改动都属于显式平台实验，不自动修改现有产品配置。

```text
CMA需求 = 静态段 + framebuffer + 其他CMA分配峰值 + 连续块/碎片余量
SW需求  = TLSF整池 + 全部任务栈 + 池外系统/IO峰值 + 连续块/碎片余量
TLSF需求 = JS + 原生UI/资源 + 包装/分配器开销 + 临时峰值 + 余量
```

JS 配额不能直接等于整池大小；要为其他使用者留下实测容量。修改后同时检查新固件 ELF/map、真实堆边界、驱动分配以及任务创建，而非只改 `JS_SetMemoryLimit`。

### 9.1 分区调整示例

当前完整压缩包的 CMA 理论余额只有 **688,432 bytes**。假设将 SW 从 4.5 MiB 增到 5 MiB，会从 CMA 拿走 524,288 bytes，余额只剩 **164,144 bytes**，还没扣其他 CMA 分配；不能据此认定可用。

旧预研里提过 SW 6 MiB。按当前完整压缩包布局推算，这需要多拿 1.5 MiB，CMA 在扣静态段和 framebuffer 后就会缺 **884,432 bytes**。因此旧建议不能原样执行。必须先减少静态占用、改变资源/代码位置，或选择更小的功能集。

精简页 CMA 余量较大，但后续恢复功能会再次增大包与静态区；不能用精简页的空闲数给完整应用扩池后就停止测量。

### 9.2 栈与显示缓冲

宿主任务栈 384 KiB，而 guest 的栈限制 256 KiB。后者是执行检查，不是另一块单独申请的 256 KiB；仍需为 C 调用和原生渲染留余量。先测编译、挂载、首帧和最复杂交互的栈高水位，字节码降低编译压力后再评估缩栈。不能仅因精简页占用低就降低完整应用的栈。

两块 framebuffer 共 510 KiB。当前驱动翻页与宿主两个 render target 配合工作，删除其中一块需要改显示策略并处理撕裂、damage 状态和同步。即便减少一块也只先释放 **255 KiB CMA**，不直接扩充 TLSF；不作为首选方案。

### 9.3 GC 只作为辅助

当前 AIC 使用约 3 MiB 的 GC threshold，并在无 damage 的空闲帧按约 2 秒间隔触发 GC。持续流量可能减少这些空闲机会。可测试页面卸载/批次结束等安全边界的回收策略，同时记录 `turn_max`。

[QuickJS-NG 内部机制文档](https://quickjs-ng.github.io/quickjs/developer-guide/internals/)说明其引用计数与循环回收机制。仍被历史、闭包、订阅或缓存持有的对象不会因强制 GC 消失；活跃编译状态和新旧 realloc 块也不是可随意回收的垃圾。频繁 GC 不能替代容量限制，还可能拖慢触摸与 IO。

## 10. 方案 G：完整功能超预算时的取舍

如果 A–F 的测量显示完整功能的**常驻工作集**已超过可用容量，应选择产品取舍，不继续靠缩小安全余量勉强启动。

- **固定 8 MiB 硬件：**优先交付有明确容量的串口/网络调试功能，终端、MCP、长历史作为可选构建变体。仍保留框架与核心逻辑，减少同时常驻功能。
- **必须同时保留完整桌面功能：**评估更大 PSRAM 的芯片/板卡及 BSP 适配。D12x 的具体封装、内存控制器和板级条件需硬件核实，不能假设焊接一颗外部 RAM 就可扩容。
- **少数数据结构确实主导：**最后评估将日志存储、字节队列或终端 cell 存储下沉原生，以固定容量结构减少 JS 对象开销。收益须减去桥接序列化和镜像副本；这会增加平台维护成本，且应先更新 SPEC，保持 `core` 不直接依赖平台 API。

不建议在当前阶段重写框架、换成另一套 UI 技术，或直接重写整个 PocketCOM。现有成功基线和已定位的容量/分配路径，已经提供了更小步的验证入口。

## 11. 实施顺序与验收门槛

### 11.1 四个交付阶段

| 阶段 | 交付物 | 进入下一阶段的条件 |
|---|---|---|
| P0 测量 | S0–S6 统计、失败分配原因、完整与精简对照记录 | 能区分编译、挂载、池外不足与连续块不足 |
| P1 板端收发闭环 | AIC 装配、紧凑 UI、容量 profile、有界测试流 | 启动/稳态/格式切换都在预算内；再逐步接 UART |
| P2 恢复选定功能 | 小回滚终端、设置、网络等逐项增量；必要时 B/C | 每加一项都保留 IO 与运行余量，不复用桌面大容量默认值 |
| P3 平台优化或取舍 | E/F 的 A/B 数据，或 G 的产品决策 | 根据完整工作集决定功能集/硬件，更新正式规格 |

若 P0 已确认编译占主要峰值，可先做 B/C 的小原型，再进入 P1；不要同时大改所有层。

### 11.2 首轮建议门槛

以下是待 P0 校准的工程目标，不是硬件厂商保证，也不是本次已经通过的结果：

- 维持现有 4,249,600-byte 池时，启动/运行的**实际分配峰值**先以不超过约 **3.25 MiB** 为目标，留约 0.8 MiB 给新增 IO、异常路径和碎片。现有 `js_pool max` 仅作辅助，不能代替实际 TLSF 空闲统计。
- 最大空闲块覆盖实测最大后续请求及其对齐/包装开销；首轮可把 **128 KiB** 作为额外观察门槛，实际若有更大请求则提高门槛或拆分请求。
- 把任务栈、驱动和 IO 实际占用加入 SW/CMA 预算。若系统池外余量不足，即使 JS 仍有空闲也不能判定通过。
- 至少 20 次冷启动、100 次页面/模式切换、30 分钟连续收发和超额突发；分别覆盖小包、长行、全字节 HEX、ANSI、暂停/恢复、清屏、断开/重连与重复开关页面。
- 无 OOM、无 native panic、无持续增长的存活内存或节点数；分配失败能记录原因并结束当前操作。过载时有准确的计数/提示，触摸可响应。
- 对比基线记录 `turn_max`、帧错误与数据处理延迟。当前精简页 61–63 fps、4–7 ms `turn_max` 只是已记录的轻负载观测，不能作为完整 UI 的既成能力。

### 11.3 验证与产物留存

现有命令可继续用于后续实现的构建与静态检查：

```sh
npm run check:aic
npm run package:aic
RTT_EXEC_PATH=/path/to/riscv-none-elf/bin npm run build:aic
bun test test/host/rtthread/
npm run typecheck
bun test test/
```

`package:aic` 不产生新固件的运行峰值，`build:aic` 的 `memory-report.json` 也只覆盖现有静态预算。实现共享模块时按改动范围回归桌面；allocator/字节码需增加对应宿主的针对性测试。烧录与真机试验另行进行。

建议将每轮包/固件 hash、配置、内存报告和原始串口日志保存到版本化的测量记录，区分“冷启动峰值”“稳态”“单次操作峰值”。当前 `.pocket/aic/probe/` 属本地诊断产物，未形成仓库内可复用的正式验收工具，不作为他人必须具备的前置。

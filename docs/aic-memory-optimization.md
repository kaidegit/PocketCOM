## 1. 先走哪条路线

一句话：**保留 PocketJS 和 Vue Vapor，以已跑通的精简入口为基线，先定位启动峰值，再恢复有明确内存上限的板端收发功能。** 精简版能启动、出帧、响应触摸，说明这条技术路线在当前硬件上走得通；但完整应用的启动图和长期数据容量完全是另一回事，不能由此推断框架所有路径都没问题。

建议的推进顺序：

1. **先补阶段测量。** 把 `bundle eval failed` 拆成编译、执行/组件挂载、首帧三个阶段，搞清楚分配失败到底发生在哪里。
2. **优先做共享 App 显式装配、节点优化与紧凑布局。** 复用同一套核心与控件，避免导入桌面 `app/session.ts` 时顺带创建所有状态和模型；同时为日志、回滚、输入与 IO 队列设板端上限。
3. **若主要卡在编译，优先验证离线 QuickJS 字节码。** 这是保留较多功能时最值得试的路线，但当前包加载链还不支持，不是换一个打包参数就能用的。
4. **同步评估 realloc 的瞬时双份分配。** 这是宿主适配层的具体优化点，不用换框架；收益要用同一个应用改造前后的峰值来证明。
5. **最后才动 PSRAM 分区、TLSF 和栈。** 先摸清 CMA、SW、最大空闲块和栈高水位，再做受控调整。资源 XIP / 缓存、更大内存硬件是更后面的选项。

| 方案 | 主要缓解什么 | 预期收益依据 | 成本 / 风险 | 建议 |
|---|---|---|---|---|
| A. 共享 App 装配、节点优化、紧凑布局 | 编译峰值、初始化与常驻对象 | 精简版已有真机成功基线 | 中；需要定义板端功能边界 | 首选 |
| B. 离线字节码，必要时真正分段加载 | 源码编译峰值 | 跳过板上源码编译；实际峰值待测 | 中高；包契约、加载器、版本兼容 | 保留完整功能时重点验证 |
| C. 改善 realloc 和分配统计 | 瞬时新旧块共存、分配开销 | 当前存在明确的 allocate-copy-free 路径 | 中；涉及对齐、分配头和失败语义 | 测量后优先实验 |
| D. 日志、终端、IO 全链路限额 | 稳态和长时间运行 OOM | 桌面容量可超过整板预算 | 中；需要确定截断、背压语义 | 接入收发前必做 |
| E. 字体资源裁剪 / flash 映射或缓存 | CMA 常驻、部分资源运行占用 | 改造前包和 `.text` 都占 PSRAM | 裁剪较低；映射/缓存较高 | 第二阶段。**代码/rodata XIP 已于 2026-10-10 实施** |
| F. CMA / SW / TLSF / 栈重配 | 空间放错区域、池外紧张 | 两区空闲不能自动互用 | 中高；可能挤压显示与系统任务 | 有数据后小步调整。**统一 TLSF 堆 + SW 7 MiB 已于 2026-10-10 实施** |
| G. 更大内存硬件 / 部分原生化 | 完整产品工作集超过 8 MiB | 改变硬上限或对象表示 | 高；硬件/BSP 或维护成本 | 明确止损条件后考虑 |

有一点要先说在前面：**这些方案的收益不能直接相加。** 裁剪、字节码和 realloc 削的很可能是同一段峰值；字体裁剪首先释放 CMA，未必给统一堆腾出空间。

前两列及真机结果来自 2026-10-09 接入记录（当时的私有池布局）；精简页大小与本地 `dist/aic/memory-report.json`、JS/PAK 文件核对过，精简页 PAK 为 **328,064 bytes**。注意：包体积变小只能证明构建裁剪有效，证明不了编译或运行工作集够小。

当时精简页的真机记录：

- JS heap 启动采样 **1,163,037 bytes**，随后 **996,688–1,007,882 bytes**。
- TLSF 分配记账启动采样 **2,284,370 bytes**，随后 **2,034,199–2,057,791 bytes**。
- TLSF 分配记账历史峰值 **2,930,837 bytes，约 2.79 MiB**。
- 池容量 **4,249,600 bytes，约 4.05 MiB**；容量减历史峰值剩 **1,318,763 bytes，约 1.26 MiB**。

这里所谓的"池用量"是 `pocketjs_heap.c` 累计的申请大小、对齐预留和包装头，**不是 TLSF 实际占用块的完整统计**，还没算 TLSF 元数据、块取整和外部碎片。那 1.26 MiB 同样不是最大连续空闲块，不能全部分配给新功能。

历史上还有一次 64 位本机编译诊断：完整 JS 压缩前后请求字节峰值约 **4,935,145 → 3,984,867 bytes**，压缩版在那套诊断的 4 MiB 限制下能编译通过，上了板照样 OOM。这组数据只用于判断优化方向——32/64 位对象布局、分配器、原生 UI 和硬件开销都不同，本机结果不能当板端验收。

### 2.1.1 XIP + 统一堆后的决定性实测（2026-10-10）

XIP/统一堆改造后，完整压缩 UI（JS 328,241 / `.pocket` 897,128）**通过了编译阶段**——板上不再报 `InternalError: out of memory`，但 mount 阶段抛 `TypeError: not a function` 后退出。本机同版本 QuickJS probe（`runtime16`，16 MiB 上限、480×272、无 com/svc）给出了裁决：

- **完整 UI 本身没有 bug**：16 MiB 上限下 mount 成功、120 帧跑通（`frames=120`，frame_errors=0）。
- **板上的 TypeError 是 OOM 的伪装**：分配失败发生在组件树构建中途，取到 undefined 方法以 TypeError 的形态抛出；不能按字面当运行时缺陷去追。
- 真实需求（heap_caps 记账，含 JS + Rust UI + 包装头）：**峰值 8,904,442 bytes（≈8.5 MiB）**、eval 后常驻 **7,951,217 bytes**、稳态 live ≈8.1 MiB，其中 QuickJS `js_heap` 4,410,058 bytes。
- 板上统一堆 7,340,032 bytes，扣除任务栈/内核/驱动后 guest+Rust 可用约 **6.0–6.4 MiB** → **缺口约 2.5 MiB（峰值口径）**，常驻口径也超约 1.6 MiB。

这次测量的结论是硬邦邦的：**完整桌面 UI 的常驻工作集超出了这块板子的 PSRAM。** 恢复完整功能只能走 **方案 A（板端专用装配 + 紧凑 UI + 容量限额）**（必要），字节码（方案 B，约省 0.9 MiB 峰值、编译期工作集）与 realloc 优化（方案 C）作为配套，或者等更大内存硬件（方案 G）。平台层的牌已经打完了——XIP 之后 PSRAM 预算与包体积彻底解耦，静态段只剩 41 KiB，想再挤也没有可挤的。

### 2.1.2 WiFi 点亮之后的内存账（2026-10-11）

2026-10-11 起产品 defconfig 带上了 RTL8189FTV WiFi（SDIO 接 SDMC0）+ third-party lwIP（netif `WL0`），真机验证到 AP 扫描为止。本次本地构建（同一份精简页包 526,568 bytes）的 `memory-report.json` 显示：

| 项目 | XIP 首日（10-10，无 WiFi） | WiFi 构建（10-11） |
|---|---:|---:|
| XIP flash 段（.text+.rodata 含内联包） | 2,037,820 | 2,660,156 |
| PSRAM 静态（.data/.bss） | 41,376 | 282,404（.data 22,960 + .bss 259,444） |
| CMA 1 MiB 扣静态+双 framebuffer 余额 | 484,960 | 243,932 |
| ITB / os 分区 | 2,054,144 / 3,145,728 | 2,686,976 / 3,145,728（余 458,752） |

解读一下：

- **省的是 flash，花的是 RAM**：驱动和 lwIP 的代码段进了 XIP（flash 多了约 620 KiB，无所谓），但 `.bss` 从 30 KiB 涨到 259 KiB——Realtek 驱动的收发缓冲、lwIP 的 pbuf/协议结构大多静态落在 PSRAM。XIP 改造好不容易把静态段压到 41 KiB，WiFi 又加回 241 KiB。
- **CMA 余额砍半**（484,960 → 243,932），好在 CMA 主要养 framebuffer，目前还不紧张；真正要盯的是 SW 统一堆。
- **§2.1.1 的"guest+Rust 可用约 6.0–6.4 MiB"是 WiFi 之前的数字。** 驱动线程、lwIP 定时器和收发缓冲都在统一堆里吃饭，`wlan wifi_on` 之后堆的基线会抬升多少还没测。下一步恢复收发功能前，必须补一组"WiFi 开/关、连 AP/断开"状态下的堆基线与峰值——否则 §2.1.1 的缺口测算会系统性偏乐观。
- ITB 涨到 2,686,976，os 分区 3,145,728 还剩 458,752。继续膨胀的话（比如恢复完整功能 + 字节码变体），分区余量也要重新看。

顺带记下板级约束：模组 EN 与 SoC 断开，使能由载板保证，固件不做电源控制；SDMC1 已关闭（原来只贡献 /sdcard 挂载失败的日志噪音）；PM 睡眠驱动未编入，固件不进睡眠。细节见 README 的 WiFi 一节。

全程 `caps_fails=0`（无一条 `rt_malloc` NULL），120 帧零错误；稳态 fps 60–62、空闲 turn_max 13–14 ms（触摸时 20 ms）；CMA 恒为 538,912/766,020（双 framebuffer 522,240 + 杂项，与 §2.1.2 静态推算吻合，实际余额 227,108）；宿主栈高水位 S4 后 48,036/393,216。

结论（对照上文的账与门槛）：

1. **口径咬合，数据可信**：`sys_max(3,369,880) − caps_peak(2,930,837) = 439,043 ≈ 384 KiB 宿主栈(393,216) + 线程/杂项`；S0-boot→S0-task 的 sys 增量 393,364 正是任务栈成本。TLSF 物理记账、heap_caps 记账、静态报告三方互相闭合。
2. **S3 编译是启动峰值，realloc 瞬时双份首次有了板上证据**（方案 C 的依据）：编译 2,749 ms，期间 realloc 109 → 63,085 次（含 5,530 次缩小）；`guest_peak − 编译产物 live ≈ 984,686 bytes` 即 allocate-copy-free 的瞬时双份开销，编译结束即回落。精简页 caps 峰值里约三分之一是 realloc transient。
3. **对照 §11.2 首轮门槛（精简页口径）全绿**：caps 峰值 2,930,837 < 4 MiB 目标；最大空闲块 3,771,972 ≫ 128 KiB；栈余量充足。注意门槛的正式对象是 P1 的板端产品功能，本行只证明测量工具链与精简基线健康。
4. **§2.1.1 的缺口推算被真机背书**：精简页板上 caps 峰值 2.79 MiB，与 runtime16 测得的完整 UI 8.9 MiB（同口径）对照，完整 UI 若上板缺口仍是 ~2.5 MiB 量级——runtime16 → 板上的外推成立。完整 UI 诊断固件的断点实测见 §2.1.4。
5. **编译占启动大头**：S2 结束到首帧 ~5.7 s 中 2.75 s 在 S3。字节码（方案 B）消的就是这段与它的 transient，对常驻缺口无救，与 §5.1 定位一致。

### 2.1.4 完整 UI 断点实测（2026-10-12，P0）

紧接 §2.1.3，完整桌面 App 诊断固件（AIC 入口临时挂 `app.tsx`，测毕已恢复精简页）：包 897,128 bytes，与 §2.1.1 的完整压缩 UI 为同一产物（SHA-256 `c161dc6a…01e2`）；ITB 3,061,760 / os 分区余 83,968，预算通过。结果一句话：**编译在板上通过，挂载执行段死于碎片化枯竭**——§2.1.1 用 runtime16 做的归因在板上复现，且这次拿到了断点数字：

|---|---:|---:|---|---:|---:|---:|---:|---:|

| S4-mount（失败） | +2,741 ms | 5,963,556 / **6,876,604** | 1,163,108 / 328,288 / **8,397** | 5,496,657 / **6,403,623** | 2,946,998 | 3,999,278 / 4,824,004 | 126,328 | 132,292 |

失败形态：`TypeError: not a function … at mount`（§2.1.1 判定的 OOM 伪装，栈顶正是 mount），随后 `bundle eval failed` + dump + 6 条 heap-fail + `run finished with code -1` 干净退出，无 panic。与精简页对照：编译 2,749→5,065 ms，guest_peak 2.34→4.05 MiB（编译 transient 985 KiB→1.65 MiB），S2 字体 atlas 多 ~243 KiB。

结论：

1. **死因是底层 `rt_malloc` NULL × 6，不是 JS 配额拒绝**：失败时 js 仅 2.95 MiB，距 5 MiB 配额很远；`caps_fails=6` 全部是对齐 8 的小请求（68/68/344/344/380/380 B）。系统历史峰值与总堆差额约 463 KiB；失败后采到 8,397 块空闲碎片、maxfree 328,288。它们支持内存压力与碎片问题，但不能据此断言失败当刻所有空闲块均小于 380 bytes；具体分配序列与即时块分布仍需补采。
2. **缺口量化更新**：板上 sys 峰值 6.88 MiB 即触顶，但"只差 463 KiB"是假象——完整挂载的真实需求仍以 runtime16 的 caps ~8.9 MiB 为准，当时推估的板上 sys 口径缺口约 **2.0 MiB**（较 §2.1.1 的 2.5 MiB 收窄，那是 WiFi 前的可用口径）。该估算混合了本机/板端及不同统计口径，不是板上成功挂载需求的实测值，也不适用于当前裁剪版本。
3. **方案权重**：A（板端装配 + 紧凑 UI + 容量限额）主线不变——容量限额同时也约束碎片增长，本数据是直接论据；C（realloc 原位扩展）证据增强（编译 transient 1.65 MiB，若削峰还能推迟触顶）；F（分区/TLSF）维持 §9.1 不动。宿主栈高水位 132,292/393,216（mount 递归深），仍在预算内。
4. **工具修正**：本轮 6 条 heap-fail 的 stage 标签停在 `S3-compile`，实际发生在执行段（标签此前只在采样点更新）；已给 `pocketjs_guest_eval_stages` 增加 EXECUTING 阶段通知，host 据此在执行前重标 `S4-mount`，下一版固件生效。

### 2.2 改造前的布局账（历史对照，2026-10-09 私有池时代）

这节留作对照，帮读者理解当初为什么判断"8 MiB 不是一个可以随便花的 JS 堆"。当时的精简固件报告展开如下，缩进项属于上层区域，不能重复相加：

| 区域 / 项目 | 大小 bytes | 说明 |
|---|---:|---|
| PSRAM 总量 | 8,388,608 | 8 MiB |
| PSRAM_CMA | 3,670,016 | 3.5 MiB；静态代码/数据、内联包、显示等 |
| ↳ 静态区域 | 2,112,656 | 包含 `.text`、`.rodata`、`.data`、`.bss` 与布局占用 |
| ↳ 内联 `.pocket` | 526,568 | **已包含在静态区域内**，不是另一笔占用 |
| ↳ 双 RGB565 framebuffer | 522,240 | `480 × 272 × 2 bytes × 2`，即 510 KiB |
| ↳ 理论剩余 | 1,035,120 | 尚未扣其他驱动分配、对齐、碎片 |
| PSRAM_SW | 4,718,592 | 4.5 MiB；系统动态堆 |
| ↳ 私有 TLSF 池 | 4,249,600 | 4,150 KiB；JS 和原生 UI 等共用 |
| ↳ PocketJS 任务栈 | 393,216 | 384 KiB；`rt_thread_create` 从系统堆申请，在池外 |
| ↳ 再扣上述任务栈后的理论剩余 | 75,776 | 74 KiB；尚未扣其他任务、设备和内核开销 |

当时还有 JS runtime 的 **4,194,304 bytes / 4 MiB 配额**。它是 TLSF 内部 JS 分配的限制，不是额外预留的一整块；原生 Rust UI 的分配经 `pocketjs_idf_rust_alloc → heap_caps_aligned_alloc` 进同一个池。这套布局有三个直接影响：

1. **`js_heap` 没到 4 MiB，TLSF 也可能先失败。** 池容量只比 JS 上限大 54 KiB，实际还要容纳原生对象、包装头与碎片；配置本身不能保证"JS 配额一定先触发"。
2. **SW 的 458 KiB 理论余额不是可自由扩池的额度。** 宿主任务栈已经需要其中 384 KiB。扩大 TLSF 可能让任务创建或未来 IO 先失败。
3. **精简包释放的是 CMA，TLSF 位于 SW，容量没有随之扩大。** 当时关闭了 memheap 自动绑定，分配失败不会自动借用 CMA；AIC 的 `heap_caps_*` 也忽略 capability 参数，切 `SPIRAM/INTERNAL` 不会自动获得第二块内存。

改造后这三条里的池内外关系虽然消失（统一堆一家），但"预算数字不等于可用余量"这条教训原样适用——现在只是换成了要同时给系统线程、WiFi/lwIP 和 guest 分同一块堆。

### 2.3 当时错误诊断缺什么证据（已被 2.1.1 部分回答）

`pocketjs_guest_eval()` 调的是 `JS_Eval(..., JS_EVAL_TYPE_GLOBAL)`，源码编译和脚本执行一次完成，而脚本执行又包含模块顶层初始化与 `mount(AicApp)`。所以当时的 **`bundle eval failed` 分不清编译 OOM 和挂载 OOM**。2026-10-10 的完整 UI 实测已经把它拆开：编译能过，挂在 mount。若后续上字节码，这条一次性 eval 的路径还会回来（反序列化 + 执行），S3/S4 分阶段测量仍然值得做。

## 3. 先补一次能指导取舍的测量

这是所有方案的共同前置。**2026-10-12 起测量工具已落地**：S0–S5 阶段采样、`heap_caps` 记账（live/peak/块数）、分配失败环形记录（charged/对齐/阶段）、TLSF 空闲块遍历（`rt_memory_walk`）、QuickJS 明细（atom/字符串/对象/函数字节码）与 copy-realloc 统计都已编入固件（默认开启，`POCKETJS_DIAG=0` 关闭），运行期用 `pjs_mem` msh 命令采样（S6/WiFi 维度）。用法与输出字段见 [host/rtthread/README.md](../host/rtthread/README.md) 的"P0 内存分阶段诊断"。尚未落地的：S6 的持续流量/页面切换矩阵（等板端收发恢复，§11.1 P1 之后）、allocator 级瞬时峰值的 tick 采样自动化、E0–E5 增量实验（属产品装配工作，见 §3.2 与方案 A）。

### 3.1 分阶段采样

| 阶段 | 边界 | 用来判断什么 |
|---|---|---|
| S0 | 系统启动、申请堆前后、创建宿主任务后 | 系统 SW 基线和栈成本 |
| S1 | 显示/触摸打开后 | CMA 动态开销与 framebuffer 之外的分配 |
| S2 | 包解析、guest 创建、UI binding / PAK 挂载后 | JS 基础环境、资源与原生 UI 基线 |
| S3 | `JS_EVAL_FLAG_COMPILE_ONLY` 返回后 | 源码编译能否独立完成 |
| S4 | 对 S3 的结果调用 `JS_EvalFunction` 后 | 顶层初始化、组件挂载峰值 |
| S5 | renderer 创建、首帧、120 tick 后 | 首帧与渲染缓存增量 |
| S6 | 各功能开启、持续流量、页面切换、清屏后 | 常驻容量、重复创建、引用未释放 |

S3/S4 的诊断要编译同一份脚本、执行一次，处理好返回值所有权，恢复原 guest 的 `frame` 获取和 jobs drain，不要又跑一遍完整 `JS_Eval`。已实现为 `pocketjs_guest_eval_stages`（guest 组件新 API），且 AIC 宿主**始终**走这条拆分路径——诊断关闭时回调为空、行为与原 `pocketjs_guest_eval` 一致——因此"分段诊断改变对象存活时间、需生产路径复验"的顾虑对 AIC 不再成立；反序列化+执行的字节码路径（§5）将来仍需同款检查。

每阶段至少记录：

- 固件与包 hash、入口/功能组合、JS/PAK 大小、区域/堆/栈配置。
- QuickJS 的 `malloc_size`、字节码/字符串/atom/对象统计；用 allocator 计数记录瞬时峰值，别只依赖每秒采样。
- TLSF 记账 current/peak、实际空闲总量、最大空闲块、失败请求的大小/对齐、发生阶段和分配来源。
- 系统 SW 与 CMA 的实际余额、任务栈高水位、native UI 节点/资源数、帧错误和 `turn_max`。

最大空闲块可在安全采样点用 SDK TLSF 的 `tlsf_walk_pool` 汇总；它要遍历块，不该在每次分配或每帧调用。分配失败路径用预留计数器或固定缓冲，别让诊断自己又去申请堆。OOM 时区分 QuickJS 配额拒绝和底层 allocator 返回 NULL；池外（现在就是统一堆里非 guest 的部分）的系统分配失败也单独记。

WiFi 启用后，S6 要加一组状态维度：`wlan wifi_on` 前后、连上 AP / 断开、有流量 / 空闲。驱动和 lwIP 的常驻与峰值不在这个矩阵里，后面的预算都是空中楼阁。

### 3.2 最小增量实验

以当时的精简入口为对照，每个实验单独构建、冷启动：

| 实验 | 新增内容 | 目的 |
|---|---|---|
| E0 | 当时精简页 | 确认基线可重复 |
| E1 | 小容量消息总线 + 纯会话装配，无完整 UI | 分离业务模型初始化成本 |

## 4. 方案 A：早期装配与紧凑 UI 评估（现由共享 UI 方案接替）

**目标：复用 PocketCOM 的核心逻辑，让板端只承担实际开放的功能和界面。**

先看清楚问题在哪。完整 `app/app.tsx` 会导入连接面板、收发区、终端、设置弹窗和 `app/session.ts`；后者在模块顶层就创建 `MessageBus`、`Terminal`、日志视图、响应式状态和订阅——即便宿主没有 `com.*`，这些导入和初始化成本照样发生。`app/locale.ts` 也会间接拉进 session，所以连共享工具的依赖边界都得查。

建议：

1. 保留 `app/main.aic.tsx → app/aic.tsx` 的独立入口，逐步把验证页替换成 480×272 紧凑产品页，不直接挂回桌面 `App`。
2. 会话装配改成显式工厂或新增板端装配模块：传入内存 profile、可用桥和启用的模型。共用 `core/`，别复制连接/编码/终端协议实现。
3. 产品功能目录、接入状态和构建取值唯一维护在根目录 `pocket.features.json`；本方案不再指定非终端功能的默认启停组合。各项拆分和设备桥接按共享 UI 路线实施、逐项测量，再更新同一份配置。WiFi/lwIP 的运行预算仍须先验证。
4. 从构建依赖中移除未启用功能。只隐藏控件、把创建动作塞进按钮回调，改变不了已打入同一 IIFE 的代码要在启动时编译的事实。
5. 界面按"连接参数页 / 收发页 / 设置页"分开挂载可见节点；卸载时释放 watchers、onFrame 注册和回调引用，别让关闭页面后对象还活着。面板沿用 absolute 布局和 Portal 约定。

好消息是接收区 `visibleRows()` 与终端 `visibleLines()` **已经做了可见范围渲染**。后续重点是验证节点复用、旧 effect 是否释放、限制模型历史，别把"加虚拟列表"当成还没兑现的大收益。

**限制：** 惰性创建终端可能改变"收发模式也持续解析 RX、切换后保留终端屏幕"的现有语义。板端若要保持该行为，就维护一个小容量终端模型，延迟的只是视图；若要完全停用后台终端，必须把 AIC 的行为差异写明。

**验收：** 不启用的模块从产物依赖中消失；每项功能都有 S3/S4/S5 增量数据；循环开关页面后模型、节点与分配用量进入稳定平台。收益按板端峰值算，不按删了多少行源码估算。

## 5. 方案 B：离线 QuickJS 字节码，必要时分段加载

### 5.1 先验证字节码能否消掉主要启动峰值

思路是在构建机上用与固件匹配的 QuickJS-NG 把应用编成字节码，板端反序列化后执行，跳过启动时的源码解析、编译期状态和字节码生成/修正。这不等于换框架，也不是把 TS 编译成机器码。

[QuickJS-NG 官方 C API 文档](https://quickjs-ng.github.io/quickjs/developer-guide/intro/)说明了预编译执行路径及其版本绑定。本地 `prepare_quickjs.py` 钉住的是 **QuickJS-NG 0.14.0 对应源码及补丁**，以这个实际实现为准，不用系统装的任意 `qjsc`。

要打通的工作：

- 构建链产出匹配的字节码，记录引擎源码/补丁、构建选项和兼容标识。32 位板端与构建机之间的兼容性靠加载测试验证，源码相同不等于兼容。
- `.pocket` 契约中 section 6 还只是预留字节码类型；当前读包逻辑强制找 NUL 结尾的 JS section。需要更新包生产、验证、C 读取、guest 加载和版本准入，桌面原路径保留。
- guest 用 `JS_ReadObject(..., JS_READ_OBJ_BYTECODE)` / `JS_EvalFunction`，保持错误处理、`frame` 注册与 jobs drain 行为。
- 只用受控构建产物，执行前核对兼容性和包完整性。字节码不是可以免校验执行的通用交换格式。
- A/B 固件分别带源码或字节码，别长期同时内联两份，否则 CMA 节省会被抵消。源码路径保留为独立诊断变体。

**能省什么：** 板上源码编译的临时工作集和启动时间。**照样要付什么：** 反序列化、atom/常量、函数/闭包、Vue 响应式对象、UI 树、日志与原生缓存。字节码文件未必比压缩 JS 小，CMA（现在主要是 `.bss` 与堆）和 flash 预算要同时看。如果 S4 挂载才是主因，字节码单独救不了——而 §2.1.1 已经实测挂载才是那道墙，所以字节码对完整 UI 的缺口（常驻口径超约 1.6 MiB）没有直接帮助，它的位置是"配合 A 降低恢复功能的启动峰值"。

只有不再依赖动态源码求值、相关测试通过后，才评估裁掉编译器代码；不能预先把它算成已经到手的 RAM 收益。

### 5.2 分段加载是另一项宿主能力

若单包仍过大，可把基础框架、收发、终端等拆成真正独立加载的单元，按阶段编译/加载，阶段之间回收临时对象。当前 AIC 产物是单一自包含 IIFE，**没有现成的按需模块加载方案**。

只改成函数封装、静态 import 后延迟调用，首次 eval 照样编译函数体。真正的分段需要构建器与宿主加载协议配合、共享一份框架运行时、避免每段重复打入 Vue，并界定卸载后的引用与订阅释放。分段只能削峰；各段对象若最终全部常驻，总工作集还会回到原量级。

**选择条件：** S3 明显高于 S4/S5 常驻值时，先做字节码原型；字节码收益不足，再评估分段。全功能常驻本身超预算的话，回到 A/D 或 G。

## 6. 方案 C：降低 realloc 的瞬时双份分配

当前共享 guest 的 `guest_realloc()` 总是：

```text
保留旧块 A → 分配新块 B → memcpy → 释放 A
```

哪怕新块更小，也要先申请另一个块。临时需要的内存不只是 `B - A`，可能是完整的 B 加包装和对齐开销。编译期数组/表扩缩容时这会放大峰值，并要求存在足够大的连续空闲块。

AIC 还有同类的 `heap_caps_realloc()` 实现，但 **`guest_realloc()` 直接调 `guest_malloc()`，并没走它**。只改下层 `heap_caps_realloc` 不会自动改善 QuickJS 的主要 realloc 路径。

分两步评估：

1. 先统计 realloc 次数、旧/新大小分布、最大单次请求与峰值时刻，确认它确实主导 OOM。
2. 为 AIC 增加保持对齐和分配头契约的 resize 路径，让 guest 走它；优先处理可原位缩小、可合并相邻空闲块的增长，失败后保留原块。SDK TLSF 提供 `tlsf_realloc`，但不能把对齐后的用户指针直接传进去：要正确处理 raw 指针、偏移、guest 头、数据移动和记账。

两个"看似优化"的坑：只把"缩小时返回原指针"当完整方案，能降低本次瞬时峰值，却可能长期占着大块容量，越省越占——若采用要同时统计实际保留容量；先 free 再 malloc 则失败时丢数据，绝不可取。

这属于 PocketJS 通用 guest / AIC port 的改进，应在对应 fork 维护，别在产品侧复制运行时。测试要覆盖 grow/shrink、零长度、失败后旧数据保留、不同对齐、数据内容与统计一致性，并回归共用 guest 的宿主。

**验收：** 同一完整包、相同堆/栈/GC 配置下，S3/S4 的失败请求减少、堆真实峰值下降、最大块足够；不能只看 JS 自报 heap。事前不承诺节省固定百分比。

## 7. 方案 D：为数据和 UI 设置板端容量

这是启动成功后的必要工作。以下风险在当时精简页上尚未发生，也不是那次启动 OOM 的已确认原因。

### 7.1 桌面默认值不适合直接搬到 8 MiB

- `core/config.ts` 默认接收历史和终端回滚均为 **10,000 行**，可配置到 100,000 行。`app/session.ts` 的日志原始字节预算为 `max(256 KiB, historyLines × 256)`，默认即 **2,560,000 bytes，约 2.44 MiB**，还没算格式化字符串和颜色数据。
- `core/logview.ts` 自身构造默认是 500 行 / 256 KiB，但完整应用显式传入配置值；只读核心默认值判断不了实际产品预算。
- `Terminal` 每行有字符串、`fg: Uint32Array`、`bg: Uint32Array`、`flags: Uint8Array`。按默认 80 列，仅属性数组就需 `80 × 9 = 720 bytes/行`；10,000 行属性约 **6.87 MiB**，还没计字符、对象和数组头。回滚逐步增长、不是构造时预分配，所以主要威胁是持续运行。
- 总线与日志历史保存相同 `Message` 的引用，不必然复制两份 payload；但保留窗口不同，任一窗口仍引用的数据都不能释放。总线的 256 KiB 上限代表不了整个应用占用。

### 7.2 建议的首轮 AIC profile

这些是实验起点，**不是现有默认值或已验证的承诺**。放在产品装配层显式注入，桌面配置不变；若开放配置导入，入口处也要套同样的板端限制。

| 对象 | 首轮建议 | 仍需计入的开销 / 行为 |
|---|---|---|
| MessageBus | 256 帧 / 64 KiB payload 双限制 | 对象头、订阅和临时 drain 数组；区分正常历史逐出与真实丢包 |
| LogView | 200 显示行、原始历史 64 KiB | 字符串、颜色、wrap 临时数据另算；不能沿用 256 KiB 下限公式 |
| Terminal | 启用时先 0–128 行回滚，列/行按实际视口 | 128×80 的属性约 90 KiB；另计当前屏、alt 屏及字符 |
| 发送编辑框 / 单次粘贴 | 4 KiB UTF-8 字节上限起步 | 拒绝或明确分块；不得默默截断要发送的数据 |
| 发送历史 | 10 条且总计不超过 8 KiB | 条数与字节数同时限制 |
| 单次 IO 事件 / 合流积累 | 1–4 KiB 事件，8–16 KiB 合流上限起步 | 达限提前产出；字节顺序不变，展示帧边界变化先补 SPEC |
| 宿主待处理队列 | 32–64 KiB 总字节上限起步，另限事件数 | 每 tick 限字节/事件数；处理速率、背压、溢出计数一起定义 |

以上不能机械相加当总内存：payload 可能共享，也可能被编解码和格式化放大。应记录所有存活对象和临时副本后的实际峰值。核心已有 `MessageBus`、`LogView`、`Terminal` 容量参数可复用；合流最大字节数等尚需新增。

### 7.3 还要堵住限制之前的峰值

`FrameCoalescer` 目前等静默间隔，不设积累字节上限。连续输入可积累多个拷贝，emit 时再创建连续 `Uint8Array`，短时间内分块和合并结果两份并存。后端总线有界也拦不住这一步先 OOM。要同时约束事件队列、合流器、单次 flush 和每 tick 工作量。

若延用 Base64/JSON 桥，一个 N 字节事件产生约 `4 × ceil(N / 3)` 个 Base64 字符，并与 JSON 字符串、解码字节、合流副本短暂共存。不能只按 payload 预算。先缩小单批并及时释放；确有测量收益再讨论二进制桥，改桥契约时同步 sim host 与测试。

显示侧要专项检查：

- HEX 文本通常扩为每字节约 3 个字符；ANSI 逐字符颜色数组会追加占用。格式切换的全历史重建必须受总字节、最大单帧和单行长度控制。
- `LogRow.fg` 的 `subarray` 保留原 ArrayBuffer；留下很短的一行也可能保活整帧颜色数组。大帧场景要测"保留字节"，不能只数可见行。
- 字符宽度缓存对不断变化的 Unicode 输入会增长；嵌入式可按烘焙字符/替换符限制缓存，或设容量上限。未知字符显示替换符，原始字节仍可通过 HEX 无损查看。
- 持续日志可按测量合并 UI 更新，避免每个小包触发整批节点重建；宿主 60Hz tick 与设备事件 FIFO 语义保留。单纯降刷新率不会减少历史数据的存活量。

暂停显示时也必须有界。TCP 可用背压；UART 没有流控、UDP 无法让发送方停下，就要明确溢出策略，通过带 `source` 的系统消息/计数告知用户。别把输入丢失伪装成正常历史逐出，也别在过载时每丢一包再造一个新消息放大队列。

**验收：** 连续无换行流、大量小帧、大包、HEX/ANSI、暂停恢复、终端主/alt 屏和格式切换都有上限；清屏/断开后存活容量回落；新限制与分帧语义有核心单测。

## 8. 方案 E：资源裁剪与真正的 flash 资源路径

### 8.1 先做低风险裁剪

精简页仍共用两份完整 i18n JSON，构建脚本从两份语言包的所有文案提取字形。可为 AIC 已启用功能生成 zh-CN/en 的 key 子集，JS 文案与烘焙字形用同一清单；动态拼接 key 和英文回退也要覆盖。减少未使用字号/字重的 atlas，维持 MiSans UI 与 JetBrains Mono 网格约定。

改造前 PAK **约 320 KiB**，是它全部的磁盘规模；不能凭字体源 TTF 很大就宣称能省几 MiB。先拆分 PAK 里各 atlas 和元数据、测实际加载开销，再评估收益。裁剪不能删掉 SPEC 要求的 ASCII、已支持界面文案和替换符；若只保留一种语言或字号，先定义 AIC 产品差异。

### 8.2 内联、文件加载和 XIP 的区别（历史）

**（本节描述的 PSRAM 布局已被 2026-10-10 的 XIP 改造取代，保留作历史依据；现状见 README"产物与内存"。）**

改造前 `.rodata` 实际位于 PSRAM_CMA，宿主直接借用内联包，没有额外整包加载副本，"去掉这份副本"并不是什么现成收益。恢复 `/rodata` 文件系统后用现有 `pocketjs_aic_run(path)` 加载，会从系统堆读整个包并因 PAK 借用长期保留——压力从 CMA 转到 SW，总 RAM 不会自动减少。

当时若要真正节省，需要以下一种新路径，而 **2026-10-10 的 XIP 改造本质就是把第一条做成了**：

- **flash 映射只读包/资源：** 确保 CPU 可直接寻址、地址生命周期满足 PAK 借用，调整 section、链接和加载流程。确认缓存/访问延迟、对齐及 DMA 访问要求；依据 ELF VMA 和真实内存采样验收。
- **分离 JS 与资源生命周期，资源按需读取：** 源码编译执行后释放其独立加载缓冲，PAK 使用有界资源缓存。当时的单块内联数组无法释放其中 JS 部分；整体解压进 RAM 也不是按需加载。
- **代码 XIP：** 当时精简固件 `.text` 为 1,298,032 bytes，提示存在可评估的代码常驻成本。XIP 首日的实测是：fps 基本无回归（60–62 对 61–63），空闲 turn_max 从 4–7 ms 涨到 12–13 ms——取指代价真实存在但稳在 60fps 帧预算内。

**剩余选择条件：** 裁剪低风险随时可做；若裁剪后 CMA 或 flash 仍紧张（比如 WiFi 继续推大 `.bss`，见 §2.1.2），再评估资源按需读取。资源访问的平均占用下降不能抵消缓存 miss 的临时峰值，启动和实际页面切换都要验证。

## 9. 方案 F：受控重配 CMA / SW / TLSF / 栈

**（SW 4.5 MiB + 私有 TLSF 池的布局已被 2026-10-10 改造取代：SW 扩为 7 MiB 统一 TLSF 系统堆、私有池删除、CMA 缩为 1 MiB。当时的分区推演保留作历史记录，公式思路仍适用于后续微调。）**

改造前的推演逻辑是：先算每个区域的峰值需求，再动地址边界。当时完整压缩包的 CMA 理论余额只有 **688,432 bytes**，把 SW 从 4.5 MiB 增到 5 MiB 要从 CMA 拿走 524,288 bytes，余额只剩 **164,144 bytes**——还没扣其他 CMA 分配。旧预研里提过的 SW 6 MiB 按当时布局推算会让 CMA 缺 **884,432 bytes**，所以那条旧建议不能原样执行，必须先减静态占用、改资源/代码位置，或选更小的功能集。现在回头看，这个死结正是 XIP 改造一次性解掉的：静态段进 flash 后，CMA 缩到 1 MiB 只养 `.data/.bss` 和 framebuffer，SW 一口气扩到 7 MiB。

改造后仍成立的公式：

```text
CMA需求 = .data/.bss + framebuffer + 其他CMA分配峰值 + 连续块/碎片余量
SW需求  = guest峰值 + 全部任务栈 + WiFi/lwIP/驱动运行缓冲 + 池外系统/IO峰值 + 余量
```

注意 JS 配额（当前 5 MiB）不能直接当整堆预算的目标值——统一堆里还住着系统线程、WiFi 驱动和 lwIP（§2.1.2）。修改后同时检查新固件 ELF/map、真实堆边界、驱动分配和任务创建，而不是只调 `JS_SetMemoryLimit`。

### 9.1 微调空间还剩多少

按 WiFi 构建（§2.1.2）：CMA 余额 243,932 bytes，SW 扣 guest 5 MiB + 系统预留 640 KiB 后余 1,441,792 bytes。看起来还有余量，但这两笔都是理论余额，没算对齐、碎片和驱动动态分配。眼下不建议再动分区；等 §3 的 S0–S6 矩阵（含 WiFi 状态维度）出数之后，如果系统侧确实吃紧，优先考虑压缩系统预留的依据（任务栈实测高水位），而不是再度缩 CMA——framebuffer 和 `.bss` 已经把它占去大半。

### 9.2 栈与显示缓冲

宿主任务栈 384 KiB，guest 的栈限制 256 KiB。后者是执行检查，不是另一块单独申请的 256 KiB；仍要为 C 调用和原生渲染留余量。先测编译、挂载、首帧和最复杂交互的栈高水位，字节码降低编译压力后再评估缩栈。不能仅因精简页占用低就降完整应用的栈。

两块 framebuffer 共 510 KiB。当前驱动翻页与宿主两个 render target 配合工作，删一块要改显示策略并处理撕裂、damage 状态和同步。即便只释放 **255 KiB CMA** 也不直接扩充 SW，不作为首选。

### 9.3 GC 只作为辅助

当前 AIC 使用约 3 MiB 的 GC threshold，无 damage 的空闲帧按约 2 秒间隔触发 GC。持续流量会减少这些空闲机会。可测试页面卸载/批次结束等安全边界的回收策略，同时记录 `turn_max`。

[QuickJS-NG 内部机制文档](https://quickjs-ng.github.io/quickjs-ng/quickjs/developer-guide/internals/)说明其引用计数与循环回收机制。仍被历史、闭包、订阅或缓存持有的对象不会因强制 GC 消失；活跃编译状态和新旧 realloc 块也不是可回收的垃圾。频繁 GC 不能替代容量限制，还会拖慢触摸与 IO。

## 10. 方案 G：完整功能超预算时的取舍

§2.1.1 的实测已经把话说得很明白：完整桌面 UI 的常驻工作集（≈8.1 MiB live）超出本板可用（WiFi 之前约 6.0–6.4 MiB，WiFi 之后更少）。如果方案 A–F 的测量进一步确认完整功能**常驻**超预算，就应该做产品取舍，而不是继续削安全余量勉强启动。

- **固定 8 MiB 硬件：** 优先交付有明确容量的串口/网络调试功能，终端、MCP、长历史作为可选构建变体。保留框架与核心逻辑，减少同时常驻的功能。
- **必须同时保留完整桌面功能：** 评估更大 PSRAM 的芯片/板卡及 BSP 适配。D12x 的具体封装、内存控制器和板级条件需硬件核实，不能假设焊一颗外部 RAM 就能扩容。
- **少数数据结构确实主导：** 最后评估将日志存储、字节队列或终端 cell 存储下沉原生，以固定容量结构减少 JS 对象开销。收益须减去桥接序列化和镜像副本；这会增加平台维护成本，且先更新 SPEC，保持 `core` 不直接依赖平台 API。

不建议在当前阶段重写框架、换 UI 技术，或整个重写 PocketCOM。现有成功基线和已定位的容量/分配路径，已经给出了更小步的验证入口。

## 11. 实施顺序与验收门槛

### 11.1 四个交付阶段

| 阶段 | 交付物 | 进入下一阶段的条件 |
|---|---|---|
| P0 测量 | S0–S6 统计（含 WiFi 状态维度）、失败分配原因、完整与精简对照记录 | 能区分编译、挂载、池外不足与连续块不足 |
| P1 板端收发闭环 | AIC 装配、紧凑 UI、容量 profile、有界测试流 | 启动/稳态/格式切换都在预算内；再逐步接 UART/WiFi |
| P2 恢复选定功能 | 小回滚终端、设置、网络等逐项增量；必要时 B/C | 每加一项都保留 IO 与运行余量，不复用桌面大容量默认值 |
| P3 平台优化或取舍 | E/F 的 A/B 数据，或 G 的产品决策 | 根据完整工作集决定功能集/硬件，更新正式规格 |

若 P0 确认编译占主要峰值，可先做 B/C 的小原型再进 P1；不要同时大改所有层。

### 11.2 首轮建议门槛

以下是待 P0 校准的工程目标，不是硬件厂商保证，也不是本次已通过的结果：

- 统一堆 7,340,032 bytes 内，guest（JS + 原生 UI + 包装头）的**实际分配峰值**首轮先以不超过约 **4 MiB** 为目标——注意 5 MiB 配额是上限不是目标值——余下约 2.4 MiB 留给系统线程栈、WiFi/lwIP 运行缓冲、IO 突发和碎片。旧版"3.25 MiB 池峰值"的口径随私有池一起作废，别再引用。
- 最大空闲块覆盖实测最大后续请求及其对齐/包装开销；首轮可把 **128 KiB** 作为额外观察门槛，实际有更大请求就提高门槛或拆分请求。
- 任务栈、驱动、WiFi/lwIP 实际占用计入 SW 预算。系统侧余量不足时，JS 还有空闲也不能判通过。
- 至少 20 次冷启动、100 次页面/模式切换、30 分钟连续收发和超额突发；分别覆盖小包、长行、全字节 HEX、ANSI、暂停/恢复、清屏、断开/重连与重复开关页面。WiFi 场景加测 `wifi_on`/连 AP/断开三种状态下的启动与稳态。
- 无 OOM、无 native panic、无持续增长的存活内存或节点数；分配失败能记录原因并结束当前操作。过载时有准确的计数/提示，触摸可响应。
- 对比基线记录 `turn_max`、帧错误与数据处理延迟。精简页 61–63 fps（XIP 后 60–62）、空闲 turn_max 12–13 ms 只是已记录的轻负载观测，不能当完整 UI 的既成能力。

### 11.3 验证与产物留存

现有命令继续用于后续实现的构建与静态检查：

```sh
npm run check:aic
npm run package:aic
RTT_EXEC_PATH=/path/to/riscv-none-elf/bin npm run build:aic
bun test test/host/rtthread/

```

两点提醒：`package:aic` 不产生新固件的运行峰值，`build:aic` 的 `memory-report.json` 只覆盖静态预算——WiFi 构建的 282 KiB `.data/.bss` 就躺在里面，但它告诉不了你驱动运行起来吃多少堆。实现共享模块时按改动范围回归桌面；allocator/字节码需增加对应宿主的针对性测试。烧录与真机试验另行进行。

建议每轮的包/固件 hash、配置、内存报告和原始串口日志存进版本化的测量记录，区分"冷启动峰值""稳态""单次操作峰值"。当前 `.pocket/aic/probe/` 是本地诊断产物，不作为他人的必备前置；**板端分阶段诊断已进固件**（见 §3 状态与 host/rtthread/README 的"P0 内存分阶段诊断"），真机串口日志直接采 `[PJS-DIAG]` 行即可；**离板探针也已入仓**（`npm run probe:aic`，同一套组件 + malloc shim，`[PJS-PROBE]` 字段与板端一致、64 位偏大 5–15%，见 host/rtthread/README 的"离板内存探针"），共享 UI / 裁剪提案的每步可先探针后上板。
